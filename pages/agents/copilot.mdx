# Setting up GitHub Copilot

Copilot reads the same Agent Skills format the rest of this section uses, so the Superhero
skill installs with a `git clone` and works without modification. What Copilot does not give
you is a scheduler, and one of its surfaces — the cloud coding agent — is a poor place to put
a private key at all. Both are covered below.

## Install

Personal, shared across your projects:

```bash
mkdir -p ~/.copilot/skills
cd ~/.copilot/skills
git clone https://github.com/superhero-com/superhero-agent-skill.git superhero
cd superhero && npm install
```

Copilot also reads personal skills from `~/.agents/skills`, and project skills from
`.github/skills`, `.claude/skills` or `.agents/skills` inside a repository. If you already have
the skill in `~/.claude/skills/superhero` for Claude Code, a symlink avoids a second copy
drifting out of date.

Clone it as `superhero` — the directory name must match the frontmatter `name`.

## Managing it in the CLI

Copilot CLI exposes skill management as slash commands:

| Command | What it does |
| --- | --- |
| `/skills list` | Show the skills Copilot has discovered |
| `/skills info superhero` | Inspect one skill and confirm it loaded |
| `/skills add` | Register an additional skills location |
| `/skills reload` | Re-scan without restarting the session |

After the clone, run `/skills reload` then `/skills info superhero`. If the skill does not
appear, the folder name or the frontmatter `name` is wrong.

## Which surfaces support it

Agent Skills are supported across Copilot CLI, the Copilot coding agent, and agent mode in
Visual Studio Code. The three differ in ways that matter a great deal for a skill that signs
blockchain transactions:

| Surface | Runs where | Suitable for this skill? |
| --- | --- | --- |
| Copilot CLI | Your machine, your shell, your environment variables | Yes. This is the surface to use |
| VS Code agent mode | Your machine, inside the editor | Yes, with the same environment-variable setup |
| Copilot coding agent | GitHub's cloud environment | **Not recommended.** See below |

### Why not the cloud coding agent

The cloud agent does not inherit your local environment. Giving it `AE_PRIVATE_KEY` means
storing a self-custodial signing key as a repository or environment secret in GitHub's
infrastructure, where its blast radius is every workflow and every collaborator with the
rights to run one. A key that can move funds is not the same kind of secret as a deploy token:
there is no revocation, no rate limit, and no chargeback. If it leaks, the wallet is drained
and there is no recourse.

If you want an unattended agent, run it on a host you control — see
[Other Agents & Runtimes](/agents/other-runtimes) — or use the OpenClaw Gateway, which was
designed for it.

## Set the key

For Copilot CLI and VS Code agent mode, the key is an ordinary environment variable in the
process that launches Copilot:

```bash
export AE_PRIVATE_KEY=<your_secret_key>
```

The same warnings apply as everywhere else in this section: a dedicated wallet, funded only
with what you can lose, and never a shell profile if you can avoid it. Read
[Wallet & Key Management](/agents/wallet-and-keys).

Copilot will not prompt you for it. Copilot's documented SKILL.md frontmatter is `name`
(required), `description`, `allowed-tools`, and a `metadata` section used for things like a
version field and the provenance that `gh skill` writes on install — there is no environment
declaration and no equivalent of OpenClaw's `primaryEnv`. The skill's `metadata.openclaw`
block is a namespace Copilot has no reason to read. Export the variable yourself before
launching, and verify with a `superhero-wallet.mjs exists` call as the first thing you ask
for.

Because five of the skill's scripts read `./contracts/` relative to the working directory, run
Copilot from the skill directory or tell it where to run the scripts from.

## Pre-approving the scripts

Copilot CLI can pre-approve shell commands, both per session and per skill, so you do not
confirm every script call.

Per session, on the command line:

```bash
copilot --allow-tool 'shell(node scripts/superhero-trending.mjs*)' \
        --allow-tool 'shell(node scripts/superhero-portfolio.mjs*)' \
        --deny-tool  'shell(node scripts/superhero-token-swap.mjs*)'
```

`shell(<glob>)` takes a glob pattern, and `--deny-tool` is the half that matters here: it is
how you run a research-only or manual-mode session where the read commands never prompt but
anything that signs still does. A bare `--allow-tool shell` approves every shell command and
is the wrong setting for a skill that holds a signing key.

Per skill, the same idea lives in SKILL.md frontmatter as `allowed-tools`, which lists the
tools Copilot may use without asking each time. Do not add `shell` or `bash` there for this
skill — GitHub's own documentation warns that pre-approving them removes the confirmation step
for terminal commands and lets an attacker-controlled skill or a prompt injection execute
arbitrary commands. A session flag you can see in your shell history is a better place for
this decision than a file that travels with the skill.

One known limitation to plan around: compound commands always prompt. Anything using `;`,
`&&`, a pipe, or a redirect triggers a permission prompt even when every individual command in
the chain would be auto-approved on its own. Keep the commands you pre-approve to single
invocations.

## Start it

> Based on the /superhero skill, start the setup guide.

Everything after that is runtime-neutral: the agent detects the key, verifies the balance,
offers a `.chain` name, and asks whether you want autonomous or manual mode.

## Scheduling: the gap

Copilot has no equivalent of OpenClaw's Gateway cron. There is nothing in the skills mechanism
that fires a prompt on a schedule, so **autonomous mode in the sense the skill means it is not
available from Copilot alone**. You have three options:

1. **Run it interactively.** Open a Copilot CLI session when you want a cycle. This is the
   honest fit for Copilot, and it pairs naturally with manual mode.
2. **Schedule the scripts, not the agent.** The twelve scripts are ordinary CLI programs. A
   cron job that runs `superhero-trending.mjs tokens 20` and pipes the JSON somewhere gives
   you the monitoring half of the loop with no model in the path at all. See
   [Other Agents & Runtimes](/agents/other-runtimes).
3. **Use a different runtime for the scheduled part.** OpenClaw's cron or a Claude Code
   print-mode cron job can drive the loop while you keep Copilot for interactive work. The
   skill is the same files; nothing is duplicated.

GitHub Actions can run a workflow on a POSIX cron `schedule` trigger, in UTC, and is the
obvious-looking fourth option — but it lands you back in the cloud-secret problem above, and
scheduled runs can be delayed or dropped under load, which is not a property you want in a
trading loop. If you use it at all, use it for read-only reporting.
