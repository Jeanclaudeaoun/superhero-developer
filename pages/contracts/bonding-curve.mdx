# BondingCurveExponential

`BondingCurveExponential.aes` computes every price in the token system. It holds no funds and
no per-community state — one instance is shared by every community, and the token sale calls
into it through the `BondingCurve.aes` interface.

Resolve its address with `factory.bonding_curve()`. The ACIs are
`BondingCurveExponential.aci.json` (the implementation) and `BondingCurve.aci.json` (the
interface the sale actually holds).

## Entrypoints

Everything here is non-stateful and free to call.

| Entrypoint | Signature | What it gives you |
| --- | --- | --- |
| `calculate_buy_price` | `(total_supply: int, count: int) => int` | Cost in aettos of buying `count` more tokens at a given supply |
| `calculate_sell_return` | `(total_supply: int, sell_tokens: int) => int` | AE returned for selling `sell_tokens` at a given supply |
| `buy_price` | `(total_supply: int) => int` | The instantaneous buy price at that supply |
| `sell_price` | `(total_supply: int) => int` | The instantaneous sell price at that supply |
| `buy_curve` | `(x: int) => Frac.frac` | The raw buy curve value as an exact rational |
| `sell_curve` | `(x: int) => Frac.frac` | The raw sell curve value as an exact rational |
| `get_k` | `() => int` | Exponent coefficient |
| `get_initial_price` | `() => int` | Curve offset constant |
| `get_minimum_count` | `() => int` | Smallest tradable count |
| `get_sell_return_percentage` | `() => int` | The sell factor numerator |
| `get_sell_return_precision` | `() => int` | The sell factor denominator |
| `curve_type` | `() => string` | Curve identifier |
| `supported_decimals` | `() => int` | Token decimals the curve is calibrated for |

The `BondingCurve` interface declares the same eight computational entrypoints with unnamed
arguments (`_1`, `_2`), which is why the sale contract's ACI shows them that way. Use the
implementation ACI when you call the curve directly.

`calculate_buy_price` and `buy_price` take a **supply**, not a count. The token sale's
`price(count)` takes a count and reads the current supply for you. Mixing them up produces
prices that are wrong by many orders of magnitude.

## Curve constants

These are the literal constants in the public Sophia source
(`superhero-com/bcl-contracts`, `contracts/BondingCurveExponential.aes`):

| Constant | Value in source | As a number |
| --- | --- | --- |
| `a` | `1 * 10 ^ 15` | 1,000,000,000,000,000 |
| `k` | `1 * 10 ^ 10` | 10,000,000,000 |
| `initial_price` | `1 * 10 ^ 11` | 100,000,000,000 |
| `decimals` | `1 * 10 ^ 18` | 10^18 |
| `minimum_count` | `1 * 10 ^ 12` | 10^12 aettos, i.e. 10^-6 of a token |
| `sell_return_percentage` | `9950` | 99.50% |
| `sell_return_precision` | `10000` | the denominator of that percentage |
| `curve_type()` | `"TAYLOR_EXPONENTIAL_V1"` | — |
| `supported_decimals()` | `18` | — |

The source carries the human-readable formula directly above them:

```text
f(x) = (0.001 * e^(0.00000001 * x)) - 0.0009999
```

## How the constants reproduce the whitepaper formula

The whitepaper states:

```text
buy(x)  = 0.001 * e^(0.00000001 * x) - 0.0009999
sell(x) = buy(x) * 0.995
```

The contract works in fixed point against `decimals = 10^18`, so each decimal constant is
that fraction scaled by 10^18:

```text
a             = 10^15  →  10^15 / 10^18 = 0.001
k             = 10^10  →  10^10 / 10^18 = 0.00000001
initial_price = 10^11  →  10^11 / 10^18 = 0.0000001
```

`a` and `k` line up exactly with the whitepaper's `0.001` and `0.00000001`. The whitepaper's
`0.0009999` offset does not appear as a single constant — it is `a - initial_price`
(`0.001 - 0.0000001` is `0.0009999`), which is how a curve pinned to `f(0) = initial_price`
is written. So `f(0)` is `0.0000001` AE per token, not zero: the very first token has a
non-zero price, which is what keeps a brand-new community from being mintable for free.

The 0.995 sell factor is `sell_return_percentage / 10000 = 9950 / 10000`. That 0.5% is the
DAO's half of the spread. The affiliation contract adds the other 0.5% on top at the sale
layer, which is how the whitepaper gets to a 1% total spread while the curve itself only
knows about 0.5%.

`curve_type()` returning `TAYLOR_EXPONENTIAL_V1` is the other half of the story, and it is
literal: the contract never evaluates a true exponential. See the next section.

## What the contract actually evaluates

FATE has no floating point, so `BondingCurveExponential.aes` replaces `e^x` with a **bounded
Maclaurin (Taylor) expansion in integer fixed point**. The closed form above is the idealised
curve the contract approximates, not the arithmetic it performs.

`calculate_price` is a difference of two expansions, not an integral evaluated symbolically:

```sophia
function calculate_price(total_supply : int, count : int) =
  require(count >= minimum_count, "MINIMUM_TOKENS_REQUIRED")
  let current_supply_exponent = (k * total_supply)
  let next_supply_exponent    = (k * (total_supply + count))
  (initial_price * count) / decimals
    + ((a * (mc2(next_supply_exponent) - mc2(current_supply_exponent))) / (k * decimals))
```

`mc2(x)` is the Maclaurin series for `e^x` **starting at the quadratic term** — it deliberately
omits the `1` and the `x` term, because those cancel in the difference and are folded into the
`initial_price * count / decimals` term:

```sophia
function mc2(x : int) = exp_helper(x, x, 0, 2, decimals * decimals)

function exp_helper(x : int, term : int, sum : int, i : int, scale : int) : int =
  if (i > 100 || term < 1)
    sum
  else
    let next_term = (term * x) / (i * scale)   // x^i / i!
    exp_helper(x, next_term, sum + next_term, i + 1, scale)
```

Two things bound the series, and both matter:

- **A hard cap of 100 iterations.** The recursion stops once `i > 100`, so at most 99 terms
  (i = 2 through 100) are ever summed. This is a gas and non-termination guard.
- **Integer truncation.** Every term is an integer division by `i * scale` with
  `scale = decimals^2 = 10^36`. The series stops early as soon as `term < 1`, because a term
  that truncates to zero makes every later term zero too. At realistic supplies the second
  condition fires long before the iteration cap.

The practical error is negligible. The published closed-form figures on
[Bonding curve](/tokens/bonding-curve) were re-checked against an exact integer replica of this
Sophia and agree to within 2e-16 AE at supply 0 and 1.4e-12 AE at supply
10,000,000 — far below one aetto of a per-token price. Quote the closed form for explanation;
quote `calculate_buy_price` for money.

`calculate_price` also carries the only hard `require` on the curve: a `count` below
`minimum_count` (10^12 aettos) aborts with `MINIMUM_TOKENS_REQUIRED`. That applies to
`calculate_buy_price` and `calculate_sell_return` alike, because both route through it.

`buy_curve` and `sell_curve` are a separate code path. They call `exp_helper` directly with a
different seeding (`exp_helper(x_exponent, decimals, decimals, 1, decimals)` — the full series
from `i = 1`, including the constant term) and return a `Frac.frac` rather than an integer.
They give you the instantaneous curve value for charting; they are not what a trade is priced
from.

## The `Frac.frac` type

```sophia
datatype frac = Pos(int, int) | Zero | Neg(int, int)
              //  numerator, denominator
```

`Frac` is the æternity standard library's exact rational type. A value is either `Zero` or a
signed numerator/denominator pair. Decoded in JavaScript it is a one-key object:

```javascript
const value = await curve.buy_curve(supply).then((r) => r.decodedResult);
// { Pos: [ 123456789n, 1000000000000n ] }   or   { Zero: [] }   or   { Neg: [ n, d ] }
```

Converting it safely means keeping it as a ratio of BigInts until the last possible moment.
Never build a JavaScript `Number` out of either half — both can exceed 2^53:

```javascript
import BigNumber from 'bignumber.js';

function fracToBigNumber(frac) {
  if ('Zero' in frac) return new BigNumber(0);
  const [num, den] = 'Pos' in frac ? frac.Pos : frac.Neg;
  const value = new BigNumber(num.toString()).dividedBy(den.toString());
  return 'Neg' in frac ? value.negated() : value;
}
```

For anything that touches money, do not convert at all. Call `calculate_buy_price` or
`calculate_sell_return`, which return integer aettos computed on chain, and use those. The
`buy_curve` and `sell_curve` entrypoints are for charting and analysis, where a rounding
error of one part in 10^18 does not matter.

## Reading the live constants

```javascript
const curveAddress = await factory.bonding_curve().then((r) => r.decodedResult);

const curve = await Contract.initialize({
  aci: JSON.parse(fs.readFileSync('./contracts/BondingCurveExponential.aci.json', 'utf8')),
  address: curveAddress,
  onNode: aeSdk.api,
});

console.log({
  k: (await curve.get_k().then((r) => r.decodedResult)).toString(),
  initialPrice: (await curve.get_initial_price().then((r) => r.decodedResult)).toString(),
  minimumCount: (await curve.get_minimum_count().then((r) => r.decodedResult)).toString(),
  sellPct: (await curve.get_sell_return_percentage().then((r) => r.decodedResult)).toString(),
  sellPrecision: (await curve.get_sell_return_precision().then((r) => r.decodedResult)).toString(),
  curveType: await curve.curve_type().then((r) => r.decodedResult),
  decimals: (await curve.supported_decimals().then((r) => r.decodedResult)).toString(),
});
```

### `get_sell_return_precision` returns the wrong constant

This is a real bug in `BondingCurveExponential.aes`, and it is worth understanding precisely
because its blast radius is narrower than it first looks. Both accessors are bound to the same
`let`:

```sophia
entrypoint get_sell_return_percentage() = sell_return_percentage  // 9950
entrypoint get_sell_return_precision()  = sell_return_percentage  // also 9950; should be
                                                                  // sell_return_precision (10000)
```

**On-chain sell math is not affected.** `calculate_sell_return` and `sell_curve` use the
let-bound constants directly, never the getters:

```sophia
entrypoint calculate_sell_return(total_supply : int, sell_tokens : int) : int =
  let price = calculate_price(total_supply - sell_tokens, sell_tokens)
  (price * sell_return_percentage) / sell_return_precision   // 9950 / 10000 = 0.995
```

So every sell that actually settles on chain returns 99.5% of the curve price, exactly as
designed. The bug only bites **off-chain callers that derive the ratio from the two getters**:
`9950 / 9950 = 1.0`, which overestimates sell returns — and therefore understates the spread —
by 0.5%.

**Do not compute the sell factor as `percentage / precision`.** Hard-code `9950 / 10000`, or
better, call `calculate_sell_return` and let the chain do the arithmetic. Treat
`get_sell_return_precision()` as unusable.

## Practical notes

- **Only 10-20% of supply is expected to be reached.** The whitepaper says so explicitly. The
  exponential is calibrated so that the price rises noticeably from the very first buys rather
  than staying flat across a long tail.
- **Price is a pure function of supply.** There is no time component, no oracle and no
  liquidity provider. Two buys of the same size at the same supply cost the same.
- **`minimum_count` is 10^12 base units.** With 18-decimal tokens that is 0.000001 of a token.
  Quotes below it are not meaningful.
