# CommunityManagement

`CommunityManagement.aes` holds everything about a community that is policy rather than
economics: who the moderators are, who is muted, how many tokens you need to hold to write,
and the community's free-form metadata.

One instance is deployed per community by the factory. Its owner is the community's DAO, so
every setting on it changes only through a DAO vote — except muting, which moderators do
directly.

Resolve it with `factory.get_community_management(token_sale)`. The ACI lives inside
`superhero-agent-skill/contracts/CommunityFactory.aci.json`; the source is
`bcl-contracts/contracts/CommunityManagement.aes` — 105 lines, and everything below is read
from it.

## Types

```sophia
type meta_info = map(string, string)

record state =
  { owner                   : address
  , minimum_token_threshold : int
  , is_private              : bool
  , moderator_accounts      : Set.set(address)
  , muted_user_ids          : Set.set(string)
  , meta_info               : meta_info }
```

`Set.set('a)` is the æternity standard library set, which is a record wrapping a map:

```sophia
record set('a) = { to_map : map('a, unit) }
```

Decoded in JavaScript the SDK gives you a `Set`, so membership is a plain `.has()`:

```javascript
const moderators = await cm.moderator_accounts().then((r) => r.decodedResult);
moderators.has('ak_alice...');   // true or false
```

## The `meta_info` map

`meta_info` is `map(string, string)` — no schema, no validation, nothing reserved. The
contract stores whatever you put in it. The keys the Superhero app writes when it creates a
community (`superhero/src/features/trending/views/CreateTokenView.tsx`) are:

| Key | What the app puts there | Where it shows up |
| --- | --- | --- |
| `collection` | the collection slug, e.g. `word` | internal |
| `description` | free text | the token page, truncated to 150 characters in the UI and 160 for the page meta description |
| `website` | a URL | the token page |
| `twitter` | an X handle or URL | the token page |

All four are optional. A community created with `new Map()` — which is what the agent skill's
`superhero-token-create.mjs` does — has no metadata at all, and the app falls back to a
generated description.

Changing metadata after creation goes through `change_meta_info`, which replaces the whole
map. There is no per-key update, so read the current map, modify it, and write it back:

```javascript
const current = await cm.meta_info().then((r) => r.decodedResult);
current.set('description', 'A new description');
// change_meta_info is owner-gated: this must go through a ChangeMetaInfo DAO vote.
```

In practice you do not call `change_meta_info` directly. The DAO does, via a
`ChangeMetaInfo(map(string, string))` vote subject.

## Events

```sophia
datatype event =
    ChangeMinimumTokenThreshold(int)
  | AddModerator(address)
  | DeleteModerator(address)
  | MuteUserId(string)
  | UnmuteUserId(string)
  | SetOwner(address)
  | ChangedMetaInfo
```

`ChangedMetaInfo` is the only event in the entire Superhero suite that carries **no
arguments** — it signals that the map changed without saying how. An indexer that wants the
new metadata has to re-read `meta_info()` when it sees this event.

## Who may call what

| Action | Caller |
| --- | --- |
| `add_moderator`, `delete_moderator` | the owner — the DAO, via an `AddModerator` / `DeleteModerator` vote |
| `change_minimum_token_threshold` | the owner — via a `ChangeMinimumTokenThreshold` vote |
| `change_meta_info` | the owner — via a `ChangeMetaInfo` vote |
| `set_owner` | the owner — this is how a `ChangeDAO` migration hands over control |
| `mute_user_id`, `unmute_user_id` | a moderator, directly |

There are exactly two guard functions behind that table, and no others in the contract:

```sophia
function require_owner() =
  require(Call.caller == state.owner, "ONLY_OWNER_CAN_CHANGE")

function require_moderator() =
  require(Set.member(Call.caller, state.moderator_accounts), "ONLY_MODERATOR_CAN_CHANGE")
```

Two things follow. **Moderators are not owners** — a moderator cannot add another moderator,
change the threshold, or touch the metadata. And **the owner is not automatically a
moderator** — the DAO cannot mute anyone without first voting itself onto the moderator set.
The initial moderator is the community creator, set once in `init`; the owner becomes the DAO
immediately afterwards.

Muting is the one action that does not need a vote. That is the design: governance sets the
policy and appoints the people, and those people act in real time.

## Initial values at creation

The factory deploys community management with fixed initial settings, from the public Sophia
source of `create_community`:

```text
Chain.create(Call.caller, 10 ^ decimals(), is_private, meta_info) : CommunityManagement
```

| Field | Initial value |
| --- | --- |
| `initial_moderator` | `Call.caller` — whoever created the community |
| `minimum_token_threshold` | `10 ^ 18`, i.e. exactly **one whole token** |
| `is_private` | whatever you passed to `create_community` |
| `meta_info` | whatever you passed to `create_community` |
| `owner` | `Call.caller` at construction, then the DAO |

The factory's own test suite asserts these values, including
`minimum_token_threshold: 10n ** 18n` and `owner` being the DAO address rewritten to `ak_`.

So the default threshold is **exactly one whole token**, `10 ^ 18` base units. It is set from a
literal in `CommunityFactory.create_community` — `Chain.create(Call.caller, 10 ^ decimals(),
...)` with `decimals() = 18` — not from a parameter, so every community starts there regardless
of what the creator asks for. Only a `ChangeMinimumTokenThreshold` vote moves it.

## What `minimum_token_threshold` actually gates

Two distinct things, one on chain and one off.

**On chain, it gates proposal creation.** `DAO.add_vote` calls
`community_management.minimum_token_threshold()` and requires the proposer's balance to meet
it, aborting with `ADD_VOTE_TOKEN_HOLDER_MISSMATCH` otherwise. That is the only on-chain reader
in the entire contract suite — nothing else in `bcl-contracts` consults it.

**Off chain, it gates the community's chat room.** The Superhero backend mirrors the on-chain
state into its `community_room` table and uses the threshold as the membership predicate for
the community's token-gated NIP-29 room
(`superhero-api/src/token-gated-rooms/services/eligibility.service.ts`):

```javascript
// eligible iff raw balance >= raw threshold AND not muted
if (muted && muted.includes(memberAddress)) return false;
return balance.gte(threshold);
```

Note that the comparison is raw-to-raw base units with no decimal shifting, and that muting is
applied as an override on top — a muted holder is ineligible however many tokens they hold.

## What a `user_id` is

`mute_user_id` and `unmute_user_id` take a `string`, not an `address`, and the contract places
no constraint on the format: `muted_user_ids` is a `Set.set(string)` and any string goes in.

The consumer, however, does constrain it in practice. The Superhero backend compares entries
from `muted_user_ids` directly against **æternity account addresses** — in
`eligibility.service.ts` the check is `muted.includes(memberAddress)`, and in
`membership-sync.service.ts` it is `room.muted.includes(row.member_address)`. An entry that is
not an `ak_...` address simply never matches anyone and mutes nobody.

So: the contract will store anything; write `ak_...` addresses if you want the mute to have an
effect in Superhero's own stack. A client reading the list should still handle unexpected
strings rather than assuming the prefix.

## What `is_private` restricts

**On chain: nothing at all.** This is worth stating flatly. `is_private` is set once in `init`
and then never read again anywhere in `CommunityManagement.aes`. There is no entrypoint that
changes it, no vote subject that targets it, and — notably — no dedicated getter for it either;
the only way to read it is the whole-state dump `get_state()`. No entrypoint on this or any
other BCL contract branches on its value.

It could not gate a read even if it wanted to. Sophia contract state is public: anyone can call
`get_state()` on any contract, and the middleware indexes it regardless. A private community's
moderators, mutes, threshold and metadata are all readable by anyone.

**Off chain: it sets one flag on the community's chat room.** The backend copies it into
`community_room.is_private` and uses it to choose the visibility tag on the NIP-29 `9002`
edit-metadata event — `public` or `private`
(`superhero-api/src/token-gated-rooms/services/room-backfill.service.ts`). The web client reads
that back and, for a private room, reports access as `auth-required` rather than rendering the
room openly (`superhero/src/features/chat/hooks/useGatedRoom.ts`). A token with no
`community_room` row defaults to public.

That is the whole of it. Treat `is_private` as a chat-room visibility preference that happens
to be stored on chain, not as a confidentiality guarantee.
