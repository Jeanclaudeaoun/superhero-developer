# Contract Events

Every state change worth watching in Superhero emits an event. This is the cross-contract
catalogue: event names, argument types, the Blake2b topic hash the middleware indexes them by,
and how to read them from a call, from the middleware, or from a live subscription.

## How an æternity event is encoded

A Sophia `Chain.event` produces a log entry with a `topics` array and a `data` field:

| Slot | Contents |
| --- | --- |
| `topics[0]` | The **Blake2b-256 hash of the event constructor name**, as a big integer. It is implicit — not one of the declared arguments. |
| `topics[1..]` | The word-sized arguments in declaration order: `address`, `int`, `bool`, contract references. |
| `data` | A single `string` argument, if the event declares one. Empty otherwise. |

`Mint(address, int)` produces three topics — the name hash, the account, and the value — and
empty data. An indexer filters logs on `topics[0]` and reads the amount from `topics[2]`.

`PostWithoutTipReceived(address, string)` produces two topics — the name hash and the author —
and puts the title in `data`.

The name hash is derivable offline:

```javascript
import { blake2b } from 'blakejs';   // or any Blake2b-256 implementation

function eventTopic(name) {
  const digest = blake2b(new TextEncoder().encode(name), undefined, 32);
  return BigInt('0x' + Buffer.from(digest).toString('hex')).toString();
}

eventTopic('Mint');
// '97248968993606906149864095761415446114204891017168990930824289305879066770211'
```

```python
import hashlib
def event_topic(name):
    return int.from_bytes(hashlib.blake2b(name.encode(), digest_size=32).digest(), 'big')
```

Two orderings are easy to transpose: `InvitationRedeemed` leads with the **invitee**, while
`InvitationRevoked` leads with the **invite address**. The third address on
`InvitationRedeemed` is the caller, which for a redemption is the invite address itself.

`UserInvited` fires only from `register_invitation`. An invite claimed through a code emits
`InvitationRedeemed` instead, even though both write the same affiliation-tree entry — watch
both to capture every invite relationship.

`RewardAdded` fires once per credited level, so one buy under a four-deep referral chain emits
four of them alongside a single `RecordSaleTransaction`.

## Name collisions — filter by contract, always

The topic hash is computed from the **name alone**. It carries no contract identity and no
argument types. Three names collide across the suite:

| Name | Emitted by | Arguments |
| --- | --- | --- |
| `Vote` | `DAOVote` | `(address, bool, int)` |
| `Vote` | `Poll` | `(address, address, int)` |
| `RevokeVote` | `DAOVote` | `(address, bool, int)` |
| `RevokeVote` | `Poll` | `(address, address)` |
| `AddModerator` / `DeleteModerator` / `ChangeMinimumTokenThreshold` | `CommunityManagement` events | also `VoteSubjects.subject` constructor names |

A `Vote` log from a governance poll and a `Vote` log from a community DAO have the same topic
hash and different argument shapes. An indexer that matches on `topics[0]` alone and then
decodes positionally will mis-parse one of them.

Filter on the emitting contract address first, then decode. The same discipline applies
within a single transaction: a token buy emits `Mint` twice, from two different token
contracts.

## Reading events from a call you made

The SDK decodes them for you against the ACI:

```javascript
const result = await sale.buy(count, { amount, omitUnknown: true });

for (const e of result.decodedEvents) {
  console.log(e.name, e.contract.address, e.args);
}
```

`decodedEvents` covers events from **every** contract the call touched, so a buy gives you the
sale's `Buy` and `PriceChange` plus both `Mint` events. Match on `e.contract.address` to tell
the community token's mint from the ProtocolDAO token's:

```javascript
const tokenMint = result.decodedEvents.find(
  (e) => e.name === 'Mint' && e.contract.address === tokenAddress,
);
```

## Reading events from the middleware

For transactions you did not submit, query the middleware's contract log index:

```text
GET {middlewareUrl}/v3/contracts/logs?contract_id={ct_...}&tx_hash={th_...}&limit=100
```

| Network | Middleware base URL |
| --- | --- |
| Mainnet | `https://mainnet.aeternity.io/mdw` |
| Testnet | `https://testnet.aeternity.io/mdw` |

Drop `tx_hash` to get a contract's full log history, paged. Each entry carries `topics` as an
array of big-integer strings and `data` as the string payload, so matching is a string compare
against the hashes above:

```javascript
const MINT_TOPIC = '97248968993606906149864095761415446114204891017168990930824289305879066770211';

const res = await fetch(
  `https://mainnet.aeternity.io/mdw/v3/contracts/logs?contract_id=${saleAddress}&limit=100`,
);
const { data } = await res.json();

const mints = data.filter((log) => log.topics?.[0] === MINT_TOPIC);
for (const log of mints) {
  console.log('account topic:', log.topics[1], 'value:', log.topics[2]);
}
```

A log entry also carries `event_hash` and, when the middleware can resolve the contract's
ACI, a decoded `event_name` and an `args` array:

```javascript
const eventHash = log.event_hash;
const eventName = log.event_name;       // may be absent
const addressTopic = log.args?.[0];     // decoded topic arguments
const payload = log.data;
```

`event_hash` is the same 32-byte Blake2b-256 digest as `topics[0]`, encoded as padded
base32hex (RFC 4648's extended-hex alphabet, not standard base32). Match on `event_hash` when
you want a stable identifier, and on `event_name` only as a convenience — it is present only
when the middleware has the contract's ACI.

Two operational notes:

- **Paginate.** The response carries a `next` field with a relative path. Follow it until it
  is absent; do not assume one page is the whole history.
- **Logs lag the transaction.** A transaction hash is available the moment it is mined, but
  the middleware may not have indexed its *logs* yet, so a `tx_hash`-filtered query can return
  an empty list for a transaction that emitted events. Retry, or reconcile in a later
  catch-up pass.

## Live subscriptions

The middleware exposes a WebSocket interface for subscribing to chain activity, so an indexer
does not have to poll `/v3/contracts/logs`.

| Network | WebSocket URL |
| --- | --- |
| Mainnet | `wss://mainnet.aeternity.io/mdw/v2/websocket` |
| Testnet | `wss://testnet.aeternity.io/mdw/v2/websocket` |

The subscribe message is a JSON object with up to four fields:

```json
{ "op": "Subscribe", "payload": "Transactions", "source": "mdw" }
```

| Field | Values |
| --- | --- |
| `op` | `Subscribe` or `Unsubscribe` |
| `payload` | the channel: `Transactions`, `MicroBlocks`, `KeyBlocks`, or `Object` |
| `target` | optional — the object to watch, for the `Object` channel |
| `source` | optional — `mdw` or `node` |

Unsubscribing sends the identical object with `op` flipped to `Unsubscribe`. Reconnect on a
timeout: a dropped socket is silent, and the gap is otherwise invisible.

The Superhero API republishes decoded token activity on its own WebSocket, which is usually
the easier integration if you only care about tokens. It emits two channels, `token-updated`
and `token-history`. See [WebSocket API](/api-reference/websocket).
