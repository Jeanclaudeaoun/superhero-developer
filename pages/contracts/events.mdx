# Contract Events

Every state change worth watching in Superhero emits an event. This page is the complete
cross-contract catalogue: the event names, their argument types, the Blake2b topic hash the
middleware indexes them by, and how to read them from a call, from the middleware, or from a
live subscription.

Every declaration here except the ProfileRegistry group has been checked against a
`datatype event` block in the Sophia source or, for `FungibleTokenFull` and `AddressLink`, a
vendored ACI. The sources are `bcl-contracts/contracts/`,
`tipping-contract/contracts/v3/Tipping_v3.aes`,
`aepp-governance/governance-contracts/contracts/`,
`superhero-agent-skill/contracts/FungibleTokenFull.aci.json` and
`superhero-api/src/plugins/address-links/aci/AddressLink.aci.json`. Every topic hash below was
recomputed from the verified constructor name.

## How an æternity event is encoded

A Sophia `Chain.event` produces a log entry with a `topics` array and a `data` field:

| Slot | Contents |
| --- | --- |
| `topics[0]` | The **Blake2b-256 hash of the event constructor name**, as a big integer. This is implicit — it is not one of the declared arguments. |
| `topics[1..]` | The word-sized arguments in declaration order: `address`, `int`, `bool`, contract references. |
| `data` | A single `string` argument, if the event declares one. Empty otherwise. |

So `Mint(address, int)` produces three topics — the name hash, the account, and the value —
and empty data, which is exactly how the Superhero backend reads it: it filters logs on
`topics[0] === MINT_TOPIC` and takes the amount from `topics[2]`.

`PostWithoutTipReceived(address, string)` produces two topics — the name hash and the author —
and puts the title in `data`.

The name hash is what the middleware's event filter matches on, and it is derivable offline:

```javascript
import { blake2b } from 'blakejs';   // or any Blake2b-256 implementation

function eventTopic(name) {
  const digest = blake2b(new TextEncoder().encode(name), undefined, 32);
  return BigInt('0x' + Buffer.from(digest).toString('hex')).toString();
}

eventTopic('Mint');
// '97248968993606906149864095761415446114204891017168990930824289305879066770211'
```

```python
import hashlib
def event_topic(name):
    return int.from_bytes(hashlib.blake2b(name.encode(), digest_size=32).digest(), 'big')
```

Every hash in the tables below was computed this way, from a constructor name read out of the
source. Four of them are independently confirmed a second way:
`superhero-com/superhero-api` hardcodes `BUY_TOPIC`, `SELL_TOPIC`, `MINT_TOPIC` and a fourth
constant that matches `PriceChange` exactly, and all four agree with the values here.

All seven argument comments above are the source's own, so the address orderings are exact.
Two of them are easy to transpose: `InvitationRedeemed` leads with the **invitee**, while
`InvitationRevoked` leads with the **invite address**. The third address on
`InvitationRedeemed` is the caller, which for a redemption is the invite address itself.

`UserInvited` fires only from `register_invitation`. An invite claimed through a code emits
`InvitationRedeemed` instead, even though both write the same affiliation-tree entry — an
indexer watching only `UserInvited` will miss every link-based invite.

`RewardAdded` fires once per credited level, so one buy under a four-deep referral chain emits
four of them alongside a single `RecordSaleTransaction`.

## Name collisions — filter by contract, always

The topic hash is computed from the **name alone**. It carries no contract identity and no
argument types. Three names collide across the suite:

| Name | Emitted by | Arguments |
| --- | --- | --- |
| `Vote` | `DAOVote` | `(address, bool, int)` |
| `Vote` | `Poll` | `(address, address, int)` |
| `RevokeVote` | `DAOVote` | `(address, bool, int)` |
| `RevokeVote` | `Poll` | `(address, address)` |
| `AddModerator` / `DeleteModerator` / `ChangeMinimumTokenThreshold` | `CommunityManagement` events | also `VoteSubjects.subject` constructor names |

A `Vote` log from a governance poll and a `Vote` log from a community DAO are
**indistinguishable by topic hash** and have different argument shapes. An indexer that
matches on `topics[0]` alone and then decodes positionally will silently mis-parse one of
them.

Filter on the emitting contract address first, then decode. The same discipline applies within
a single transaction: a token buy emits `Mint` twice, from two different token contracts.

## Reading events from a call you made

The SDK decodes them for you against the ACI:

```javascript
const result = await sale.buy(count, { amount, omitUnknown: true });

for (const e of result.decodedEvents) {
  console.log(e.name, e.contract.address, e.args);
}
```

`decodedEvents` covers events from **every** contract the call touched, so a buy gives you the
sale's `Buy` and `PriceChange` plus both `Mint` events. Match on `e.contract.address` to tell
the community token's mint from the ProtocolDAO token's:

```javascript
const tokenMint = result.decodedEvents.find(
  (e) => e.name === 'Mint' && e.contract.address === tokenAddress,
);
```

## Reading events from the middleware

For transactions you did not submit, query the middleware's contract log index. The Superhero
backend uses this exact endpoint:

```text
GET {middlewareUrl}/v3/contracts/logs?contract_id={ct_...}&tx_hash={th_...}&limit=100
```

| Network | Middleware base URL |
| --- | --- |
| Mainnet | `https://mainnet.aeternity.io/mdw` |
| Testnet | `https://testnet.aeternity.io/mdw` |

Drop `tx_hash` to get a contract's full log history, paged. Each entry carries `topics` as an
array of big-integer strings and `data` as the string payload, so matching is a string compare
against the hashes above:

```javascript
const MINT_TOPIC = '97248968993606906149864095761415446114204891017168990930824289305879066770211';

const res = await fetch(
  `https://mainnet.aeternity.io/mdw/v3/contracts/logs?contract_id=${saleAddress}&limit=100`,
);
const { data } = await res.json();

const mints = data.filter((log) => log.topics?.[0] === MINT_TOPIC);
for (const log of mints) {
  console.log('account topic:', log.topics[1], 'value:', log.topics[2]);
}
```

### The middleware's own `event_hash`, and how it is encoded

A middleware log entry carries more than `topics` and `data`. It also has `event_hash` and,
when the middleware can resolve the contract's ACI, a decoded `event_name` and an `args` array.
The Superhero backend matches on either:

```javascript
const eventHash = log.event_hash;
const eventName = log.event_name;       // may be absent
const addressTopic = log.args?.[0];     // decoded topic arguments
const payload = log.data;
```

`event_hash` is the **same 32-byte Blake2b-256 digest as `topics[0]`, encoded as padded
base32hex** — RFC 4648's extended-hex alphabet, not standard base32. That is verifiable
offline against the constants the backend hardcodes:

```python
import hashlib, base64
def event_hash(name):
    return base64.b32hexencode(hashlib.blake2b(name.encode(), digest_size=32).digest()).decode()

event_hash('Link')    # '6SB35NM6QMV5IG8BGTLL5O77IU72C5E3OC63PB4KHNDNSS83HAOG===='
event_hash('Unlink')  # 'EIE1QPIL7TJBARSE513J05U144N3D9Q0MB4PQ69VATC40VROO3IG===='
```

Both of those match `LINK_EVENT_HASH` and `UNLINK_EVENT_HASH` in
`superhero-api/src/plugins/address-links/address-links-plugin-sync.service.ts` exactly. Use
standard base32 and every comparison silently fails, because the two alphabets produce
different strings for the same bytes.

Match on `event_hash` when you want a stable identifier, and on `event_name` only as a
convenience — it is present only when the middleware has the contract's ACI, so it can be
absent for a contract the middleware has never seen.

Two operational notes, both learned the hard way in the Superhero backend:

- **Paginate.** The response carries a `next` field with a relative path. Follow it until it
  is absent; do not assume one page is the whole history.
- **Logs lag the transaction.** A transaction hash is available the moment it is mined, but
  the middleware has not necessarily indexed its *logs* yet, so a `tx_hash`-filtered query can
  return an empty list for a transaction that definitely emitted events. Retry, or reconcile in
  a later catch-up pass. The Superhero backend carries a source comment about exactly this
  failure mode.

## Live subscriptions

The middleware exposes a WebSocket interface for subscribing to chain activity, so an indexer
does not have to poll `/v3/contracts/logs`.

| Network | WebSocket URL |
| --- | --- |
| Mainnet | `wss://mainnet.aeternity.io/mdw/v2/websocket` |
| Testnet | `wss://testnet.aeternity.io/mdw/v2/websocket` |

The subscribe message is a JSON object with up to four fields. This is the shape the Superhero
backend sends in production (`superhero-api/src/ae/websocket.service.ts`, with the type in
`src/utils/types.ts`):

```json
{ "op": "Subscribe", "payload": "Transactions", "source": "mdw" }
```

| Field | Values |
| --- | --- |
| `op` | `Subscribe` or `Unsubscribe` |
| `payload` | the channel: `Transactions`, `MicroBlocks`, `KeyBlocks`, or `Object` |
| `target` | optional — the object to watch, for the `Object` channel |
| `source` | optional — `mdw` or `node` |

Unsubscribing sends the identical object with `op` flipped to `Unsubscribe`. The Superhero
backend sends the unsubscribe once per source value rather than tracking which one it
subscribed with, and reconnects after a 20-second timeout when the socket drops — worth copying,
since a dropped socket is silent and the gap is otherwise invisible.

The Superhero API in turn republishes decoded activity on its own WebSocket, which is usually
the easier integration if you only care about tokens. It emits exactly two channels —
`token-updated` and `token-history` — from `TokenWebsocketGateway`. The web app also registers
listeners for `token-created` and `token-transaction`, but the backend emits neither, so those
never fire. There are no `@SubscribeMessage` handlers on the gateway either: the relay was
removed as a security fix, so a client `message` emit is dropped and delivery is at-most-once.

## Open questions

- **The query parameter name for server-side event filtering.** The encoding is now settled —
  padded base32hex of the Blake2b digest, as shown above — but the Superhero backend never
  passes it as a filter; it fetches by `contract_id` (plus `tx_hash`) and matches `event_hash`
  client-side. Whether `/v3/contracts/logs` accepts an `event_hash=` or similar parameter, and
  what it is called, would be settled by the middleware's own OpenAPI document at
  `{middlewareUrl}/v3/api`, which was unreachable while this page was written. Client-side
  filtering on `topics[0]` or `event_hash` always works regardless.
- **What `target` accepts on the `Object` channel.** The subscribe message shape is now
  settled from the Superhero backend's own client, but that client only ever subscribes to
  `Transactions`, `MicroBlocks` and `KeyBlocks` — it declares the `Object` channel and never
  uses it, so nothing in the repository shows what a `target` looks like or whether a contract
  address is a valid one. The [ae_mdw repository](https://github.com/aeternity/ae_mdw) is the
  place to settle it.
- **Whether the ProfileRegistry event names are exactly as the whitepaper spells them.** The
  six hashes in that section are correct only if the names are, and neither an ACI nor a source
  file for `ProfileRegistry.aes` exists in any repository available here. The contract now
  looks retired, so this may never be settleable — and may not be worth settling. What would
  close it: the `ProfileRegistry.aes` source, or the deployed address plus a decompile.
