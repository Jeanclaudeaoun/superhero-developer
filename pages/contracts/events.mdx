# Contract Events

Every state change worth watching in Superhero emits an event. This page is the complete
cross-contract catalogue: the event names, their argument types, the Blake2b topic hash the
middleware indexes them by, and how to read them from a call, from the middleware, or from a
live subscription.

Unless noted, every declaration here is taken from a `datatype event` block in a vendored ACI
or in the public Sophia source. The one exception is the ProfileRegistry group, which comes
from whitepaper prose — see the note in that section.

## How an æternity event is encoded

A Sophia `Chain.event` produces a log entry with a `topics` array and a `data` field:

| Slot | Contents |
| --- | --- |
| `topics[0]` | The **Blake2b-256 hash of the event constructor name**, as a big integer. This is implicit — it is not one of the declared arguments. |
| `topics[1..]` | The word-sized arguments in declaration order: `address`, `int`, `bool`, contract references. |
| `data` | A single `string` argument, if the event declares one. Empty otherwise. |

So `Mint(address, int)` produces three topics — the name hash, the account, and the value —
and empty data, which is exactly how the Superhero backend reads it: it filters logs on
`topics[0] === MINT_TOPIC` and takes the amount from `topics[2]`.

`PostWithoutTipReceived(address, string)` produces two topics — the name hash and the author —
and puts the title in `data`.

The name hash is what the middleware's event filter matches on, and it is derivable offline:

```javascript
import { blake2b } from 'blakejs';   // or any Blake2b-256 implementation

function eventTopic(name) {
  const digest = blake2b(new TextEncoder().encode(name), undefined, 32);
  return BigInt('0x' + Buffer.from(digest).toString('hex')).toString();
}

eventTopic('Mint');
// '97248968993606906149864095761415446114204891017168990930824289305879066770211'
```

```python
import hashlib
def event_topic(name):
    return int.from_bytes(hashlib.blake2b(name.encode(), digest_size=32).digest(), 'big')
```

Every hash in the tables below was computed this way. Four of them are independently
confirmed: `superhero-com/superhero-api` hardcodes `BUY_TOPIC`, `SELL_TOPIC`, `MINT_TOPIC` and
a fourth constant that matches `PriceChange` exactly, and all four agree with the values here.

## Name collisions — filter by contract, always

The topic hash is computed from the **name alone**. It carries no contract identity and no
argument types. Three names collide across the suite:

| Name | Emitted by | Arguments |
| --- | --- | --- |
| `Vote` | `DAOVote` | `(address, bool, int)` |
| `Vote` | `Poll` | `(address, address, int)` |
| `RevokeVote` | `DAOVote` | `(address, bool, int)` |
| `RevokeVote` | `Poll` | `(address, address)` |
| `AddModerator` / `DeleteModerator` / `ChangeMinimumTokenThreshold` | `CommunityManagement` events | also `VoteSubjects.subject` constructor names |

A `Vote` log from a governance poll and a `Vote` log from a community DAO are
**indistinguishable by topic hash** and have different argument shapes. An indexer that
matches on `topics[0]` alone and then decodes positionally will silently mis-parse one of
them.

Filter on the emitting contract address first, then decode. The same discipline applies within
a single transaction: a token buy emits `Mint` twice, from two different token contracts.

## Reading events from a call you made

The SDK decodes them for you against the ACI:

```javascript
const result = await sale.buy(count, { amount, omitUnknown: true });

for (const e of result.decodedEvents) {
  console.log(e.name, e.contract.address, e.args);
}
```

`decodedEvents` covers events from **every** contract the call touched, so a buy gives you the
sale's `Buy` and `PriceChange` plus both `Mint` events. Match on `e.contract.address` to tell
the community token's mint from the ProtocolDAO token's:

```javascript
const tokenMint = result.decodedEvents.find(
  (e) => e.name === 'Mint' && e.contract.address === tokenAddress,
);
```

## Reading events from the middleware

For transactions you did not submit, query the middleware's contract log index. The Superhero
backend uses this exact endpoint:

```text
GET {middlewareUrl}/v3/contracts/logs?contract_id={ct_...}&tx_hash={th_...}&limit=100
```

| Network | Middleware base URL |
| --- | --- |
| Mainnet | `https://mainnet.aeternity.io/mdw` |
| Testnet | `https://testnet.aeternity.io/mdw` |

Drop `tx_hash` to get a contract's full log history, paged. Each entry carries `topics` as an
array of big-integer strings and `data` as the string payload, so matching is a string compare
against the hashes above:

```javascript
const MINT_TOPIC = '97248968993606906149864095761415446114204891017168990930824289305879066770211';

const res = await fetch(
  `https://mainnet.aeternity.io/mdw/v3/contracts/logs?contract_id=${saleAddress}&limit=100`,
);
const { data } = await res.json();

const mints = data.filter((log) => log.topics?.[0] === MINT_TOPIC);
for (const log of mints) {
  console.log('account topic:', log.topics[1], 'value:', log.topics[2]);
}
```

Two operational notes, both learned the hard way in the Superhero backend:

- **Paginate.** The response carries a `next` field with a relative path. Follow it until it
  is absent; do not assume one page is the whole history.
- **Logs lag the transaction.** A transaction hash is available the moment it is mined, but
  the middleware has not necessarily indexed its *logs* yet, so a `tx_hash`-filtered query can
  return an empty list for a transaction that definitely emitted events. Retry, or reconcile in
  a later catch-up pass. The Superhero backend carries a source comment about exactly this
  failure mode.

## Live subscriptions

The middleware exposes a WebSocket interface for subscribing to chain activity — key blocks,
micro blocks, and objects such as a particular contract — so an indexer does not have to poll
`/v3/contracts/logs`. The Superhero API in turn republishes decoded activity on its own
WebSocket channels (`token-created`, `token-updated`, `token-transaction`, `token-history`),
which is usually the easier integration if you only care about tokens.

## Open questions

- **The exact middleware query parameter for filtering by event name.** The æternity protocol
  documentation states that the middleware accepts a base32hex-encoded Blake2b hash of the
  event constructor name as an event filter, but the parameter name and encoding were not
  confirmed against a live middleware. The `contract_id` + `tx_hash` form above is verified
  from working Superhero backend code; client-side filtering on `topics[0]` always works.
- **The exact middleware WebSocket subscribe payload.** The interface is documented as
  supporting key blocks, micro blocks and object subscriptions, but the precise JSON message
  shape was not read. See the
  [ae_mdw repository](https://github.com/aeternity/ae_mdw) for the current WebSocket docs.
- **Argument meanings for `InvitationRedeemed`, `InvitationRevoked` and
  `RecordSaleTransaction`.** Types are known from the ACI; no source comment naming the
  arguments was read.
- **Whether the ProfileRegistry event names are exactly as the whitepaper spells them.** The
  hashes above are only correct if they are. No ACI or source was available to confirm.
