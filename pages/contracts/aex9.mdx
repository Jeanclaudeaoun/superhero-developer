# FungibleTokenFull (AEX-9)

`FungibleTokenFull.aes` is the AEX-9 implementation every Superhero token uses — each
community's token and the ProtocolDAO token alike. It is the æternity fungible token
reference implementation with the allowance, mintable, burnable and swappable extensions.

There is no single address. Community tokens are deployed by the factory and resolved with
`factory.token_contract(collection_name, name)` or `sale.token_contract()`. The ProtocolDAO
token is at `ct_dsa6octVEHPcm7wRszK6VAjPp1FTqMWa7sBFdxQ9jBT35j6VW` on mainnet, or from
`factory.protocol_dao_token()`.

The ACI is `superhero-agent-skill/contracts/FungibleTokenFull.aci.json`. This is the one
contract in the Superhero suite whose Sophia source is not vendored anywhere — it is pulled in
as a dependency. `bcl-contracts/package.json` pins it exactly:

```text
"aeternity-fungible-token": "git+https://git@github.com/aeternity/aeternity-fungible-token#v2.2.0"
```

and the BCL contracts include it by path, as
`include "../node_modules/aeternity-fungible-token/contracts/fungible-token-full.aes"`. So the
authoritative text for anything the ACI does not answer is
`contracts/fungible-token-full.aes` at tag **v2.2.0** of that repository. The `tipping-contract`
repository pins the same tag.

## Types

```sophia
record meta_info =
  { name     : string
  , symbol   : string
  , decimals : int }

record allowance_accounts =
  { from_account : address     // the owner of the tokens
  , for_account  : address }   // the spender

type balances   = map(address, int)
type allowances = map(allowance_accounts, int)

record state =
  { owner        : address
  , total_supply : int
  , balances     : balances
  , meta_info    : meta_info
  , allowances   : allowances
  , swapped      : map(address, int) }
```

`allowance` takes the `allowance_accounts` record as a **single argument**, not two
addresses — pass an object with exactly those two field names:

```javascript
const current = await token
  .allowance({ from_account: 'ak_owner...', for_account: 'ak_spender...' })
  .then((r) => r.decodedResult);
```

## Events

```sophia
datatype event =
    Transfer(address, address, int)     // from, to, value
  | Allowance(address, address, int)    // owner, spender, value
  | Burn(address, int)                  // account, value
  | Mint(address, int)                  // account, value
  | Swap(address, int)                  // account, value
```

These are the standard AEX-9 events. A single token buy produces a `Mint` on the community
token *and* a `Mint` on the ProtocolDAO token, in the same transaction — see
[Events](/contracts/events) for how to tell them apart.

## Decimals

Superhero community tokens are created with **18 decimals**. The value is not a guess: the
Superhero app passes `18n` explicitly when converting an initial buy count
(`superhero/src/features/trending/libs/createCommunity.ts`), and the bonding curve's
`decimals` constant is `10 ^ 18`.

So one whole token is `1000000000000000000` base units, the same scale as AE itself. Every
`value`, `count` and `amount` in these contracts is in base units.

The 18 is also enforced in two places on chain. `CommunityFactory` hardcodes it —
`function decimals() = 18` — and passes it to every token it creates, and the sale contract
refuses a curve calibrated for anything else:

```sophia
require(decimals == bonding_curve.supported_decimals(),
        "BONDING_CURVE_SUPPORTED_DECIMALS_MISSMATCH")
```

`BondingCurveExponential.supported_decimals()` returns `18`.

## How a community token is constructed

The sale contract creates it, in its own `init`:

```sophia
token_contract = Chain.create(name, decimals, symbol, None) : FungibleTokenFull
```

Three consequences worth knowing before you integrate:

- **The `owner` is the sale contract**, because `Chain.create` runs inside it. That is what
  authorises `mint` on a buy and `burn` on a sell, and it is why nobody else can mint.
- **`initial_owner_balance` is `None`**, so a new community token starts at zero total supply.
  Every token in existence was minted by a buy.
- **The name and the symbol are the same string.** `CommunityFactory.create_community` passes
  its `name` argument to both positions. Do not expect `meta_info().name` and
  `meta_info().symbol` to differ for a community token.

Do not hardcode it anyway. Read `meta_info()` and use the `decimals` field — the ProtocolDAO
token and any future collection could differ:

```javascript
const meta = await token.meta_info().then((r) => r.decodedResult);
const whole = new BigNumber(rawBalance.toString()).shiftedBy(-Number(meta.decimals));
```

## The allowance model

Two Superhero flows require an allowance before they will work:

| Flow | Grant the allowance to |
| --- | --- |
| Selling tokens back to the bonding curve | the **sale** contract address, `ct_` rewritten to `ak_` |
| Voting in a community DAO | the **vote** contract address, `ct_` rewritten to `ak_` |

The `ct_` to `ak_` rewrite is real and required. A contract's account identity uses the `ak_`
prefix over the same key bytes, and that is the address that appears as `for_account`:

```javascript
const forAccount = saleAddress.replaceAll('ct_', 'ak_');
```

Three entrypoints manage the value, and they are not interchangeable:

| Entrypoint | Semantics | When to use it |
| --- | --- | --- |
| `create_allowance(for_account, value)` | Creates a new allowance entry. | First time granting to this spender |
| `change_allowance(for_account, value_change)` | Adds a **delta** to an existing allowance. The delta may be negative. | Adjusting an existing allowance |
| `reset_allowance(for_account)` | Sets it to zero. | Revoking |

The correct pattern, straight from the agent skill's `superhero-token-swap.mjs`:

```javascript
const existing = await token
  .allowance({ from_account: aeSdk.address, for_account: forAccount })
  .then((r) => r.decodedResult)
  .catch(() => undefined);

if (existing === undefined) {
  await token.create_allowance(forAccount, amount);
} else {
  const delta = new BigNumber(amount).minus(existing.toString()).toFixed();
  await token.change_allowance(forAccount, delta);
}
```

`allowance` returns `option(int)`, so a never-granted allowance decodes to `undefined`. The
`.catch(() => undefined)` guards the case where the contract aborts on a missing entry rather
than returning `None`.

`allowance_for_caller(from_account)` is the same read from the spender's side — useful when
the spender wants to check what it may move without knowing its own address twice over.

## Mint and burn

`mint` and `burn` are how supply tracks the bonding curve:

- **Buy** → the sale contract calls `mint(buyer, count)`. Supply goes up.
- **Sell** → the sale contract pulls your tokens with `transfer_allowance` and calls `burn`.
  Supply goes down.

Both are owner-gated. For a community token the owner is the sale contract, so you cannot mint
yourself tokens — the only way to increase supply is to pay the curve. This is what makes
`total_supply()` a trustworthy input to a price calculation.

## The swap extension

`swap`, `swapped` and `check_swap` come from the AEX-9 swappable extension. They exist to
migrate balances from an older token contract into a newer one: `swap()` credits the caller
based on their balance in the predecessor and records the amount in the `swapped` map.

Whether any Superhero community token has actually used this path is not determined — see
Open questions. For a token created by the factory today, `swapped` is empty and these
entrypoints are inert.

`aex9_extensions()` returns the list of extension names this contract implements. Call it
rather than assuming; it is the standard's own discovery mechanism.

## Reading balances

| Read | Returns | Note |
| --- | --- | --- |
| `balance(account)` | `option(int)` | `undefined` when the account has never held the token, **not** zero |
| `balances()` | `map(address, int)` | Every holder. Large on popular tokens — prefer the middleware |
| `total_supply()` | `int` | The input to every bonding curve price call |

For holder lists and balances at scale, query the middleware's AEX-9 endpoints
(`/v3/aex9/<contract address>`) rather than calling `balances()`, which returns the entire map
in one response.

## Open questions

All four of these are answerable from one file that is not present here:
`contracts/fungible-token-full.aes` at tag **v2.2.0** of
[aeternity/aeternity-fungible-token](https://github.com/aeternity/aeternity-fungible-token),
which is the exact revision `bcl-contracts` pins. Read that, and all four close at once.

- **Which extensions `aex9_extensions()` actually reports.** The entrypoint exists in the ACI
  and the presence of `swap`, `mint`, `burn` and the allowance family implies
  `["allowances", "mintable", "burnable", "swappable"]`, but the literal list is in the source,
  not the ACI, and was not read.
- **Whether `change_allowance` reverts on a negative result.** The ACI types `value_change` as a
  plain `int`, so a negative delta is well-typed. What happens when it would drive the allowance
  below zero — abort, or clamp — is in the source.
- **Whether `create_allowance` aborts when an allowance already exists.** The agent skill
  branches on existence and calls `change_allowance` instead, which strongly implies it does.
  The allowance example above is correct either way.

One of the original four is now settled negatively: **`swap` is not used anywhere in
Superhero.** A search across `superhero-api/src` and `superhero/src` for `swap()`, `swapped()`
and `check_swap` returns no call site in either — every `swap` hit in the backend belongs to the
DEX, which is unrelated. The AEX-9 migration mechanism exists in the implementation and
Superhero has never exercised it. If you want to be certain for a particular token, call
`swapped()` on it; a non-empty map would mean otherwise.
