# Accounts API

Everything the API knows about an `ak_...` address: its profile fields and links, the tokens it
holds, its portfolio value over time, its realized and unrealized PnL, and where it sits on the
trading leaderboard. This is the richest part of the API and the part agents lean on hardest.

All paths are relative to `https://api.superhero.com`. Reads need no authentication.

## Endpoints

| Method & path | Query | Returns |
| --- | --- | --- |
| `GET /api/accounts` | `search`, `order_by`, `order_direction`, `has_nostr`, `limit`, `page` | Paginated account rows |
| `GET /api/accounts/{address}` | — | One account aggregate |
| `GET /api/accounts/search` | `q`, `limit` | Typeahead matches |
| `GET /api/accounts/chain-names` | `addresses` | Batch address to `.chain` name map |
| `GET /api/accounts/by-nostr` | `pubkeys` | Nostr pubkey to account map |
| `GET /api/accounts/{address}/tokens` | `order_by`, `order_direction`, `limit`, `page`, `search`, `owner_address`, `creator_address`, `factory_address` | Paginated holdings |
| `GET /api/accounts/{address}/portfolio/history` | `startDate`, `endDate`, `interval`, `convertTo`, `include` | Array of value snapshots |
| `GET /api/accounts/{address}/portfolio/tokens/history` | same | Snapshots with per-token PnL |
| `GET /api/accounts/{address}/portfolio/value` | `convertTo` | Latest value only |
| `GET /api/accounts/{address}/portfolio/stats` | `startDate`, `endDate` | Trading statistics |
| `GET /api/accounts/{address}/portfolio/pnl-chart.svg` | `startDate`, `endDate`, `convertTo`, `background`, `height`, `width` | An SVG sparkline |
| `GET /api/accounts/{address}/pnl` | `blockHeight` | PnL at a block height |
| `GET /api/accounts/leaderboard` | `window`, `sortBy`, `sortDir`, `page`, `limit`, `minAumUsd`, `startDate`, `endDate`, `tradingOnly` | Ranked traders |

Note the casing split: the account-scoped portfolio endpoints and the leaderboard use
**camelCase** `startDate` / `endDate`, unlike the snake_case `start_date` / `end_date` used
everywhere under `/api/analytics`. See [Conventions](/api-reference/conventions).

## `GET /api/accounts/{address}`

Returns the account aggregate the web app types as `AccountAggregate`:

| Field | Type | Meaning |
| --- | --- | --- |
| `address` | string | The `ak_...` |
| `bio` | string or null | Legacy bio field |
| `chain_name` | string or null | Legacy `.chain` name field |
| `chain_name_updated_at` | string or null | ISO 8601 |
| `links` | object or null | Verified address links, see below |
| `profile` | object or null | Profile payload, see [Profile](/api-reference/profile) |
| `public_name` | string or null | Resolved display name |
| `x_username` | string or null | Legacy X handle field |

`links` is where the current, verified identity lives:

| Key | Meaning |
| --- | --- |
| `x` | Verified X handle |
| `bio` | Verified bio text |
| `prefaens` (also `prefered_aens_name`) | Preferred `.chain` name |
| `site` | Verified website |

The `links`, `profile` and top-level fields are three generations of the same data. The web app
reads them with an explicit precedence — `links` first, then `profile`, then the legacy
top-level field:

```ts
// getLinkedXUsername, src/api/backend.ts
account?.links?.x ?? account?.profile?.x_username ?? account?.x_username
```

Do the same, and strip a leading `@` from the X handle as the app does.

```bash
curl -s "https://api.superhero.com/api/accounts/ak_2ruXgsLy9jMwEqsgyQgEsxw8chYDfv2QyBfCsR6qtpQYkektWB"
```

## `GET /api/accounts`

| Parameter | Notes |
| --- | --- |
| `search` | `ILIKE` across the account's `address` and `chain_name` and the profile cache's `public_name`, `chain_name`, `username` and `fullname`. Rejected above 100 characters |
| `order_by` | Default `total_volume`. See the row table below for the full set; anything outside it is a 400 |
| `order_direction` | `ASC` or `DESC`, default `DESC`. Anything else is a 400 |
| `has_nostr` | `true` or `1` restricts to accounts with a non-empty `links.nostr` |
| `limit`, `page` | `limit` defaults to 100, must be 1–100. Cached 60 seconds |

### What a list row contains

A row is the `Account` entity
(`superhero-api/src/account/entities/account.entity.ts`), returned whole:

| Field | Type | Sortable | Meaning |
| --- | --- | --- | --- |
| `address` | string | | The `ak_...`, primary key |
| `bio` | string or null | | Legacy bio |
| `chain_name` | string or null | | Cached `.chain` name |
| `chain_name_updated_at` | string or null | | Last successful resolution |
| `total_volume` | string | yes | Lifetime trade volume in **AE** — a `numeric` column, so a string |
| `total_tx_count` | number | yes | All indexed trades |
| `total_buy_tx_count` | number | yes | |
| `total_sell_tx_count` | number | yes | |
| `total_created_tokens` | number | yes | |
| `total_invitation_count` | number | yes | Invitations issued |
| `total_claimed_invitation_count` | number | yes | |
| `total_revoked_invitation_count` | number | yes | |
| `links` | object | | A `jsonb` map, `{}` when empty — the verified links described above |
| `banned` | boolean | | |
| `created_at` | string | yes | ISO 8601 |

One column exists but is never returned: `chain_name_checked_at` is declared `select: false`
because it is sweep bookkeeping, not account data.

Searching by an `ak_...` that the table has not seen triggers a hydration attempt from the
transactions table first, so a brand-new trader can be found by their exact address.

```bash
curl -s "https://api.superhero.com/api/accounts?order_by=total_volume&order_direction=DESC&limit=10"
```

## Name resolution helpers

Two endpoints exist specifically so a feed does not have to make one request per row:

- **`GET /api/accounts/chain-names?addresses=ak_a,ak_b`** returns a map of address to `.chain`
  name or `null`. Every valid address you send is present in the result; invalid ones are
  silently dropped and **at most 25 are resolved** per call.
- **`GET /api/accounts/search?q=alice&limit=8`** is typeahead. `limit` is clamped to 1–20, default
  8, `q` is capped at 100 characters, and a `q` shorter than the minimum returns `[]` rather than
  an error. Items are `AccountSearchResultDto`: `address` and `chain_name`.

`GET /api/accounts/by-nostr?pubkeys=...` takes comma-separated npub or 64-character hex keys, at
most 200, and returns the matching accounts.

## `GET /api/accounts/{address}/tokens`

An account's holdings.

| Parameter | Notes |
| --- | --- |
| `order_by` | Only `balance`. Anything else is a 400 |
| `order_direction` | `ASC` or `DESC`, default `DESC` |
| `search` | `ILIKE` on the token's name |
| `factory_address` | Restrict to one factory. **Without it the list is restricted to the current factory** |
| `creator_address` | Switches modes — see below |
| `owner_address` | Switches modes — see below |
| `limit`, `page` | `limit` defaults to 100, must be 1–100 |

There is **no `includes` parameter** here; the token is always nested. Each item is a holder row
with a `token` object attached, and that token carries a freshly computed `rank`:

```json
{
  "id": "...", "aex9_address": "ct_...", "address": "ak_...",
  "balance": "1500000000000000000000", "block_number": 1104233,
  "last_tx_hash": "th_...", "created_at": "2026-05-02T11:04:19.000Z",
  "token": { "rank": 17 }
}
```

Balances are in **token base units** — divide by 10 raised to the token's `decimals`. Because
`limit` is capped at 100, an unfiltered fetch only ever returns the top 100 holdings by balance;
use `search` to narrow rather than paging blindly.

### `creator_address` and `owner_address` change what the endpoint means

Pass either and the handler switches to a different query entirely: it lists **tokens the path
address created or owns**, regardless of balance, and attaches whatever balance exists (or the
string `"0"`). Without them, it lists tokens the path address *holds a positive balance in*.

The value you pass is used only as a flag — the query filters on the **path** address, not on the
value. So `?owner_address=ak_ANYTHING` on `/api/accounts/ak_ALICE/tokens` returns Alice's owned
tokens. Pass the same address as the path to avoid confusion.

```bash
# Tokens Alice holds
curl -s "https://api.superhero.com/api/accounts/ak_YOUR_ADDRESS/tokens?order_by=balance&order_direction=DESC&limit=50"

# Tokens Alice created, including any she has sold out of
curl -s "https://api.superhero.com/api/accounts/ak_YOUR_ADDRESS/tokens?creator_address=ak_YOUR_ADDRESS&limit=50"
```

## Portfolio history

`GET /api/accounts/{address}/portfolio/history` returns a **bare JSON array** of snapshots, not a
paginated envelope.

| Parameter | Default | Notes |
| --- | --- | --- |
| `startDate` | 90 days ago | ISO 8601. Validated as a date string |
| `endDate` | now | ISO 8601. Capped at the current time — you cannot ask for the future |
| `interval` | `86400` | Reconstruction spacing **in seconds**; 86400 is daily. Must be a positive integer |
| `convertTo` | `ae` | One of the nine currency codes; anything else is a 400 |
| `include` | — | Comma-separated. `pnl` adds aggregate `total_pnl`; `pnl-range` switches to daily-window PnL instead of cumulative |

### Nothing here is a stored snapshot

`interval` is not a sampling rate over a snapshot table — there is no snapshot table. Each
timestamp you ask for is **reconstructed from scratch**
(`superhero-api/src/account/services/portfolio.service.ts`):

1. The requested range is walked in `interval`-second steps, generating a list of timestamps. Any
   timestamp in the future is dropped, and the loop is bounded at 100,000 iterations.
2. Each timestamp is resolved to a **block height** in one batch query against the indexed
   `key_blocks` table. A timestamp the table cannot cover falls back to the nearest already
   resolved height rather than to genesis.
3. The account's AE balance is read from the node **at that height**, deduplicated per unique
   height and cached within the request.
4. Token holdings and PnL at that height are computed from the `transactions` table in one batched
   query across every unique height.

So a 3600-second `interval` gives you real hourly reconstructions, not interpolation between daily
rows — and every extra point costs real work. That is why this is the slowest endpoint in the API
and why the web app allows it 90 seconds.

The reach backwards is bounded by the indexer, not by a retention policy: history goes back as far
as the mirrored `key_blocks` and `transactions` tables do, which for the community-token data is
the factory's deployment height. **The default range is the last 90 days**, plus one day when you
supply neither `startDate` nor `endDate`.

Each snapshot is a `PortfolioHistorySnapshotDto`:

| Field | Type | Meaning |
| --- | --- | --- |
| `timestamp` | string | ISO 8601 |
| `block_height` | number | Height at the snapshot |
| `ae_balance` | number | Bare AE held, in **AE** |
| `usd_balance` | number | USD value of the AE balance |
| `tokens_value_ae` | number | Value of all token holdings, in AE |
| `tokens_value_usd` | number | The same in USD |
| `total_value_ae` | number | `ae_balance` plus `tokens_value_ae` |
| `total_value_usd` | number | The same in USD |
| `ae_price` | number | AE/USD rate at the snapshot |
| `version` | number | Snapshot format version |
| `total_pnl` | `TotalPnlDto` | Only when `include` requests it |
| `tokens_pnl` | object | Per-token breakdown keyed by `sale_address`. **Only** from `/portfolio/tokens/history` |

Unlike the token fields, these are plain numbers already in AE and USD — no 1e18 division.

`TotalPnlDto`:

| Field | Type | Meaning |
| --- | --- | --- |
| `percentage` | number | Total PnL as a percentage |
| `invested` | `PnlAmountDto` | Total invested |
| `current_value` | `PnlAmountDto` | Current total value |
| `gain` | `PnlAmountDto` | Total gain or loss |

`PnlAmountDto` is simply an `ae` and a `usd` number.

### Cost basis is weighted average, and `include` changes what "PnL" means

There is no FIFO or LIFO lot matching anywhere in the PnL code. Cost basis is the **weighted
average purchase price** across the account's entire history with a token
(`superhero-api/src/account/services/bcl-pnl.service.ts`), and `create_community` counts as a buy
alongside `buy`.

The `include` flag selects between two different definitions:

| Mode | `invested` | `gain` |
| --- | --- | --- |
| **Cumulative** (default, or `include=pnl`) | everything ever spent on the token | `proceeds_from_all_sells + current_value_of_holdings - total_spent` |
| **Range** (`include=pnl-range`) | `average_cost_per_token * tokens_sold_in_the_window` | `proceeds_in_window - that_cost_basis` |

Cumulative PnL therefore includes unrealised gains on open positions; range PnL is **realised
only**, deliberately, so a daily calendar only turns green or red when a position is actually
closed. The average cost used to price a range sale is the all-time average, not a
window-restricted one — that is how a token bought last year and sold today gets the right cost
basis.

`percentage` is `gain_ae / cost_basis_ae * 100`, and is 0 rather than infinite when the cost basis
is 0.

Holdings at a given block height are computed with a strict inequality —
`tx.block_height < snapshot_height` — so a trade in the snapshot's own block is not counted yet.

```bash
curl -s "https://api.superhero.com/api/accounts/ak_YOUR_ADDRESS/portfolio/history?interval=86400&convertTo=ae&include=pnl"
```

This is the slowest endpoint in the API — the web app allows it 90 seconds before aborting. Bound
it with `startDate` and `endDate` rather than asking for all history at a fine `interval`.

For a live ticker use **`GET /api/accounts/{address}/portfolio/value`** instead, which returns
just `{ value, timestamp }` and takes `convertTo` of `ae` or `usd`.

## `GET /api/accounts/{address}/portfolio/stats`

`TradingStatsResponseDto` — realized trading quality over a date range. `startDate` defaults to
30 days ago (inclusive), `endDate` to now (exclusive).

| Field | Type | Meaning |
| --- | --- | --- |
| `top_win` | `PnlAmountDto` | Largest single realized gain from any sell in the range |
| `unrealized_profit` | `PnlAmountDto` | Current unrealized profit across all tokens still held — **all-time holdings, not date-filtered** |
| `win_rate` | number | Percentage of sells in the range that produced a positive gain |
| `avg_duration_seconds` | number | Average hold time from first buy to sell |
| `total_trades` | number | Sell transactions in the range |
| `winning_trades` | number | Sells with a positive gain |

`GET /api/accounts/{address}/pnl?blockHeight=N` gives point-in-time PnL instead:
`block_height`, `total_pnl` and a `tokens_pnl` map keyed by sale address. `blockHeight` defaults
to the current height.

## `GET /api/accounts/leaderboard`

Ranked traders. Two modes:

- **Precomputed window.** Pass `window` of `7d`, `30d` or `all`. Metrics are precomputed per
  window.
- **Custom period.** Pass `startDate` **and** `endDate` together. Leaders are then ranked by
  selected-period performance among accounts that traded in that range, and both the top-level
  metrics and the buy/sell counts are scoped to it. Pass `tradingOnly=true` to base period PnL and
  ROI on realized token-trading PnL only, excluding transfer-driven portfolio changes.

| Parameter | Notes |
| --- | --- |
| `sortBy` | `pnl`, `roi`, `mdd` or `aum` |
| `sortDir` | Defaults to `DESC`, except `sortBy=mdd` which defaults to `ASC` |
| `minAumUsd` | Exclude leaders below this USD AUM |
| `page`, `limit` | The web app uses `limit=18` |
| `points`, `maxCandidates` | Both deprecated and currently ignored |

Items carry `address`, `chain_name`, `aum_usd`, `pnl_usd`, `roi_pct`, `mdd_pct`, `buy_count`,
`sell_count`, `volume_usd`, `created_tokens_count`, `owned_trends_count` and
`portfolio_value_usd_sparkline` (an array of `[timestamp, value]` pairs).

`mdd_pct` is **maximum drawdown as a positive percentage**: 0 means the portfolio never fell from
a peak, and a larger number is worse. The computation walks the sparkline, tracks the running
peak and keeps the largest `(peak - value) / peak`, then multiplies by 100 — it can never be
negative. That is why `sortDir` defaults to `ASC` for this one metric: ascending puts the
steadiest portfolios first.

The `meta` here is **not** the standard envelope: it carries `page` (not `currentPage`), `limit`,
`totalItems`, `totalPages`, `window`, `sortBy`, `sortDir` and a `timeFilter` of
`value`, `unit`, `start` and `end`. Snapshot-backed windows are rebuilt by a cron every ten
minutes.

**Responses are cached for up to 60 seconds**, and `meta.timeFilter.start` / `end` reflect when
the cache entry was filled rather than the moment of your request.

```bash
curl -s "https://api.superhero.com/api/accounts/leaderboard?window=30d&sortBy=roi&sortDir=DESC&limit=18&page=1"
```
