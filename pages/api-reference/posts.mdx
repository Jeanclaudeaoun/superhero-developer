# Posts API

Superhero posts live on chain; this API is the indexed, queryable copy of them. Use it to read a
feed, load a thread, search post content, or find everything one account has written — without
scanning the chain yourself.

All paths are relative to `https://api.superhero.com`. Reads need no authentication. **Posting is
not a REST operation** — a post is a contract call, so writing goes through the chain, not
through this API. See [Posting](/social/posting).

## Endpoints

| Method & path | Query | Returns |
| --- | --- | --- |
| `GET /api/posts` | `order_by`, `order_direction`, `search`, `account_address`, `topics`, `limit`, `page` | Paginated `PostDto` |
| `GET /api/posts/popular` | `page`, `limit`, eight ranking weights, `debug` | Paginated `PostDto`, ranked |
| `GET /api/posts/{id}` | — | One `PostDto`. `{id}` accepts a **slug** too |
| `GET /api/posts/{id}/comments` | `order_direction`, `limit`, `page` | Paginated comment thread |
| `GET /api/feed` | `sort`, `cursor`, `limit` | Cursor-paginated union of posts, token creations and trades |
| `GET /api/topics` | `order_by`, `order_direction`, `search`, `limit`, `page` | Paginated topics |
| `GET /api/topics/name/{name}` | — | One topic with its posts |
| `GET /api/topics/popular/trending` | — | Most-used topics by post count |
| `GET /api/tips/posts/{postId}/summary` | — | Total tipped on a post |
| `GET /api/tips` | `order_by`, `order_direction`, `sender`, `receiver`, `type`, `post_id`, `limit`, `page` | Paginated tips |
| `GET /api/tips/accounts/{address}/summary` | — | Tips sent and received by an account |
| `GET /api/posts/analytics` | `start_date`, `end_date`, `sender_address` | Daily posting volume series |
| `GET /api/posts/analytics/top-posters` | `start_date`, `end_date`, `limit` | Leaderboard of authors |
| `GET /api/posts/analytics/top-topics` | `start_date`, `end_date`, `limit` | Leaderboard of topics |

## `PostDto`

Transcribed from `src/api/generated/models/PostDto.ts`.

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string | Unique post identifier |
| `tx_hash` | string | `th_...` of the transaction that created the post |
| `tx_args` | array of objects | Raw contract-call arguments as JSON |
| `sender_address` | string | Author `ak_...` |
| `sender` | `PostSenderDto` | Inlined author profile — `address`, `public_name`, `bio`, `avatarurl` |
| `contract_address` | string | `ct_...` of the posting contract |
| `type` | string | See below — the contract entrypoint on a single post, the literal `post` on a list |
| `content` | string | The post body |
| `trend_mentions` | array of `PostTrendMentionDto` | Hashtags in `content` resolved to tokens |
| `media` | array of strings | Media URLs attached to the post |
| `total_comments` | number | Comment count |
| `created_at` | string | ISO 8601 |

`PostTrendMentionDto` turns a `#HASHTAG` in the body into something you can render as a live
price chip:

| Field | Type | Meaning |
| --- | --- | --- |
| `name` | string | The trend name, without the `#` |
| `sale_address` | string or null | Token sale address, when a token exists for that name |
| `collection_info` | `CollectionInfoDto` or null | Collection metadata for that token |
| `performance` | `TrendPerformanceSummaryDto` or null | `past_24h`, `past_7d`, `past_30d`, `all_time` price movement |

Netlify's SEO edge function also reads `updated_at` and `slug` off the single-post response.
Neither is on the generated `PostDto`, but both are real columns on the `posts` entity — along
with `post_id` (the parent, null on a top-level post), `is_hidden`, `token_mentions` and
`version`.

### What `type` actually holds

There is no curated enum. On a single post, `type` is **the name of the contract entrypoint that
created it** — the indexer writes `type: tx.function || 'unknown'`
(`superhero-api/src/social/services/post.service.ts`). The posting contract is a single
deployment per network (`ct_2Hyt9ZxzXra5NAzhePkRsDPDWppoatVD7CtHnUoHVbuehwR8Nb` on mainnet), so in
practice you will see that contract's entrypoint name, or the literal `unknown` for a row whose
function could not be read.

The distinctions you might expect `type` to carry are **not** in it. Whether a post is a comment,
whether it is hidden, and whether it was generated by a token launch or a trade are all encoded in
the transaction's *second* argument — a string array the indexer scans for the markers
`comment:<parentId>`, `hidden`, `bcl:` and `bcl-tx:` (`PostService.detectPostType`). A comment
surfaces as a non-null **`post_id`**, not as a `type` value.

On the **list** endpoints (`/api/posts`, `/api/posts/popular`) the controller overwrites the field
outright with the literal string `post` before returning each row, so `type` there is a constant
and carries no information at all.

### The `/api/feed` discriminator is a different vocabulary

`GET /api/feed` has its own three-value union, declared in
`superhero-api/src/feed/feed.controller.ts`:

```text
'post' | 'token_created' | 'trade'
```

Those are feed-item kinds assigned by the feed controller, unrelated to `PostDto.type`. See the
`/api/feed` section below.

## `GET /api/posts`

| Parameter | Notes |
| --- | --- |
| `order_by` | `total_comments` or `created_at` |
| `order_direction` | `ASC` or `DESC` |
| `search` | Filters by content or topic |
| `account_address` | Only posts by this `ak_...` |
| `topics` | Comma-separated topic names, partial matching |
| `limit`, `page` | Standard pagination, `limit` capped at 100 |

```bash
# Newest 20 posts mentioning a topic
curl -s "https://api.superhero.com/api/posts?topics=superhero&order_by=created_at&order_direction=DESC&limit=20"
```

## `GET /api/posts/popular`

The main feed. Ranking is **all-time with a temporary freshness boost for new posts** — the
`window` parameter still exists but is explicitly deprecated in the generated client: *"Popular
ranking is now all-time; this value is accepted for backwards compatibility and ignored."* Do not
build against it.

What you can tune are eight per-request weights. Each takes `low`, `med` (the default) or `high`,
and shifts how much one signal contributes to the score:

| Parameter | Signal |
| --- | --- |
| `comments` | Comment count |
| `tipsAmountAE` | Total AE tipped |
| `tipsCount` | Number of tips |
| `uniqueTippers` | Distinct tipping accounts |
| `trendingBoost` | Whether the post mentions a trending topic |
| `contentQuality` | Server-side content quality signal |
| `reads` | Read count |
| `interactionsPerHour` | Engagement velocity from comments, tips and unique tippers per hour |

Defaults are `page=1` and `limit=50`. Passing `debug=1` returns the ranking breakdown alongside
the items.

```bash
# A feed that leans on tips rather than comments
curl -s "https://api.superhero.com/api/posts/popular?limit=20&tipsAmountAE=high&comments=low"
```

Note the casing: the query key is `tipsAmountAE`, capital AE, while the rest are lowerCamelCase.

## `GET /api/posts/{id}` — and yes, it takes a slug

One post, by **either** its id or its slug. The handler matches both in one query:

```sql
WHERE (post.id = :id OR post.slug = :id) AND post.is_hidden = false
```

So this works directly, with no search step:

```bash
curl -s "https://api.superhero.com/api/posts/hello-world-2f8a91c4"
```

The Netlify SEO renderer's search-then-fetch dance is therefore unnecessary; it predates the slug
match. Note the `is_hidden = false` clause: a hidden post is a 404 here, not an empty body.

The path segment is validated before the lookup — it must start with a letter or digit and may
then contain letters, digits and `. _ ~ : -`, up to 128 characters. Anything else is a 400.

Slugs are generated from the content: the first 60 characters, lowercased, with everything that is
not a letter, digit, `.`, `_`, `~` or `-` collapsed to a single `-`, then the first underscore-
delimited segment of the post id appended. They are not guaranteed unique, so an id is still the
safer key when you have one.

## `GET /api/posts/{id}/comments`

Paginated thread under a post. Takes `order_direction` (`ASC` or `DESC`), `limit` and `page` —
note that unlike `/api/posts` there is no `order_by`; comments are ordered by time.

Comments are themselves posts in this model, so items follow the same `PostDto` shape.

## `GET /api/feed`

The combined home feed, and the only cursor-paginated endpoint in the API.

| Parameter | Notes |
| --- | --- |
| `sort` | `latest` or `hot` |
| `cursor` | Opaque cursor from the previous response's `next_cursor` |
| `limit` | Page size |

`sort=latest` is a keyset-paginated union of **posts, token creations and trades**. `sort=hot`
returns posts only, ranked by the same algorithm as `/api/posts/popular` — trades and token
creations are never ranked under Hot.

`limit` defaults to **20** and is clamped to 1–50 — lower than the 100 used elsewhere, and a
clamp rather than a 400. An unrecognised `sort` is a 400. Responses are cached for 15 seconds.

Response shape:

```json
{
  "items": [
    { "type": "post", "created_at": "2026-09-13T09:14:02.000Z", "data": {} }
  ],
  "next_cursor": "..."
}
```

Each item is a discriminated union. `type` is one of exactly three values:

| `type` | `data` is |
| --- | --- |
| `post` | A post row, the same shape as a `/api/posts` item |
| `token_created` | A token row, as on `/api/tokens` |
| `trade` | A transaction row, as on `/api/transactions` |

Under `sort=hot` only `post` items are returned — trades and token creations are never ranked.
`next_cursor` is `null` on the last page; pass it straight back as `cursor` and do not parse it.
A cursor minted under one `sort` is ignored by the other, so switching sort restarts from the top.

No component in the web app calls `/api/feed` today — it renders its feed from `/api/posts` and
`/api/posts/popular` instead.

## Topics

A topic is a hashtag with a post count. `GET /api/topics/name/{name}` returns the topic with its
`posts` array and `post_count`; the web app uses `post_count` to render "N posts" on a token's
topic feed and falls back to counting the array when the field is absent.

`GET /api/topics` takes `order_by` of `name`, `post_count` or `created_at`, plus
`order_direction`, `search`, `limit` and `page`. `GET /api/topics/{id}` accepts either a UUID or
a name.

```bash
curl -s "https://api.superhero.com/api/topics/popular/trending"
```

Topics are the social side of the same names that become tokens. See
[Trending & Topics](/api-reference/trending) for how a tag maps to a token.

## Tips

`GET /api/tips/posts/{postId}/summary` is the one tip endpoint the web app actually calls. It
returns `totalTips`, a **string that the app treats as a number** — parse it rather than
comparing it.

```bash
curl -s "https://api.superhero.com/api/tips/posts/123/summary"
```

`GET /api/tips` lists individual tips, ordered by `amount`, `type` or `created_at`, with filters
for `sender`, `receiver`, `type` and `post_id`. The web app uses it to show who tipped a post,
combining `post_id` and `receiver` into one indexed query rather than paging the receiver's whole
transaction history:

```bash
curl -s "https://api.superhero.com/api/tips?post_id=123&receiver=ak_YOUR_ADDRESS&order_by=created_at&order_direction=DESC&limit=100"
```

A tip row (`superhero-api/src/tipping/entities/tip.entity.ts`):

| Field | Type | Meaning |
| --- | --- | --- |
| `tx_hash` | string | `th_...` of the tipping transaction, the primary key |
| `type` | string | `profile` (the default) or `post` |
| `sender_address` | string | The tipper. The row also carries a joined `sender` account object |
| `receiver_address` | string | The recipient, with a joined `receiver` account object |
| `post_id` | string or null | The tipped post, null for a profile tip |
| `amount` | string | Tip size **in AE** — no 1e18 division |
| `created_at` | string | ISO 8601 |

`order_by=amount` sorts on `CAST(amount AS numeric)` rather than lexically, so the ordering is
numerically correct despite the string column.

`GET /api/tips/accounts/{address}/summary` returns two fields:

```json
{ "totalTipsSent": "12.5", "totalTipsReceived": "3.25" }
```

Both are AE totals as decimal strings, and both **exclude self-tips** — a row whose sender and
receiver are the same address contributes to neither. `GET /api/tips/posts/{postId}/summary` 404s
for an unknown post id rather than returning a zero.

## Posting analytics

Three endpoints under `/api/posts/analytics`, all taking `start_date` and `end_date` as
`YYYY-MM-DD`. Defaults are the last 10 days. A start after the end, or an unparseable date, is a
400.

### `GET /api/posts/analytics`

A bare array, one element per day, computed live from the `posts` table (the cron-backed
`post_analytics` table exists but is deliberately bypassed so a backfill gap never shows):

| Field | Type | Meaning |
| --- | --- | --- |
| `date` | string | `YYYY-MM-DD` |
| `total_posts` | number | Top-level posts that day (`post_id IS NULL`) |
| `total_comments` | number | Comments that day |
| `total_all` | number | Both together |
| `total_unique_posters` | number | Distinct authors that day |
| `cumulative_total_posts` | number | Running total up to and including that day |
| `avg_comments_per_post` | number | |

Hidden posts are excluded throughout. `sender_address` scopes every figure to one author.
`GET /api/posts/analytics/past-24-hours` returns the same object for a rolling 24-hour window.

### `GET /api/posts/analytics/top-posters`

`limit` defaults to 10 and is clamped to 1–100. Each item:

```text
sender_address · total_posts · total_comments · total_all · public_name
```

Ordered by `total_all` descending. `public_name` is resolved from the profile cache and **falls
back to the address** when no profile exists — it is never null, so do not use it to test for a
profile.

### `GET /api/posts/analytics/top-topics`

Each item is `topic_id`, `topic_name` and `post_count` for the range, ordered by `post_count`
descending. Same `limit` handling.

`GET /api/posts/analytics/preview` is a server-rendered HTML dashboard, not JSON.
