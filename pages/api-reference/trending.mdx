# Trending & Topics API

Trending is the entry point for most agent strategies: find what is moving, then find whether a
token exists for it. Two surfaces do this — **trending tags**, which are scored words ingested
from external providers, and **topics**, which are hashtags that have actually been used in posts
on Superhero.

All paths are relative to `https://api.superhero.com`. Reads need no authentication.

## Endpoints

| Method & path | Query | Returns |
| --- | --- | --- |
| `GET /api/trending-tags` | `order_by`, `order_direction`, `search`, `limit`, `page` | Scored tags, each with its matching token joined in |
| `GET /api/trending-tags/{tag}` | — | One tag, without the token join |
| `POST /api/trending-tags` | — | Ingest tags from an external provider. **Needs an API key** |
| `GET /api/topics` | `order_by`, `order_direction`, `search`, `limit`, `page` | Paginated topics |
| `GET /api/topics/{id}` | — | One topic, by UUID or name |
| `GET /api/topics/name/{name}` | — | One topic, by name |
| `GET /api/topics/popular/trending` | — | Most-used topics by post count |
| `GET /api/tokens` with `order_by=trending_score` | — | Tokens ranked by trending score |
| `GET /api/tokens/{address}/score` | — | A token's full trending-score breakdown |
| `GET /api/tokens/{address}/trending-eligibility` | — | Whether a token qualifies for the trending list |
| `GET /api/search` | `q`, `limit` | Tokens, accounts and posts in one call |

## `GET /api/trending-tags`

| Parameter | Notes |
| --- | --- |
| `order_by` | `score` (default), `source` or `created_at`. **Anything else is a 400** |
| `order_direction` | `ASC` or `DESC`, default `DESC`. Anything else is a 400 |
| `search` | Substring match on the tag, `ILIKE`. Rejected above 100 characters |
| `limit`, `page` | `limit` defaults to 100 and must be 1–100; outside that range it is a 400 |

`order_by=token_sale_address` — which some hand-written clients still send — **is rejected** with
`400 Invalid order_by value: token_sale_address`. The allow-set in
`superhero-api/src/trending-tags/controllers/trending-tags.controller.ts` is literally
`new Set(['score', 'source', 'created_at'])`, and there is no such column on the entity. Clients
carrying that enum are out of date.

```bash
curl -s "https://api.superhero.com/api/trending-tags?order_by=score&order_direction=DESC&limit=20"
```

### Item shape

A row is the `TrendingTag` entity
(`superhero-api/src/trending-tags/entities/trending-tags.entity.ts`):

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | number | Auto-increment row id |
| `tag` | string | The normalised tag, unique |
| `description` | string or null | Always null today — nothing writes it |
| `score` | number | The provider's score, as sent |
| `source` | string | The `provider` string from the ingest call |
| `created_at` | string | ISO 8601 |

The list endpoint additionally attaches a nested **`token`** object via
`leftJoinAndMapOne('trending_tag.token', 'token', 'token', 'token.name = trending_tag.tag')`.
That join — tag equals token *name* — is the token association. There is no
`token_sale_address` column; take `token.sale_address` off the nested object, and expect `token`
to be absent or null for a tag with no matching token.

`GET /api/trending-tags/{tag}` returns the bare entity for one tag, with **no** `token` join. It
normalises the path parameter the same way ingest does, so `/superHero` finds `SUPER-HERO`. It
404s with `Trending tag not found` when there is no row.

### `score` — what scale, and is it comparable?

`score` is whatever the provider sent, parsed with `parseFloat`. The backend applies **no**
normalisation, no cap and no rescaling (`TrendingTagsService.createTrendingTags`). There is no
documented range.

Scores are nevertheless comparable *within a response*, for a reason that is easy to miss: a
`POST /api/trending-tags` with a non-empty `items` array calls `repository.clear()` — it
**truncates the whole table** — before inserting. So the table always holds exactly the most
recent ingest batch, from one provider, on one scale. You will not see two providers' magnitudes
mixed in the same listing; you will see the last one to post.

The practical consequence is that `score` is a ranking key, not a quantity. Sort by it; do not
compare it across time, and do not attach units to it.

### `source` — where a trend comes from

Trending tags are **ingested from external providers**, not derived from Superhero activity.
`POST /api/trending-tags` takes a `provider` string plus an array of `tag` / `score` items, and
`source` on a read row is that `provider` verbatim. The DTO's `x`, `facebook` and `github` are
examples in the Swagger annotation, not an allow-list: `provider` is validated only as a
non-empty string, so any value can land in `source`.

The backend has no scheduled pull of its own. `TrendingTagsService.saveAllTrendingTags`, gated by
`PULL_TRENDING_TAGS_ENABLED`, has a `// TODO` for a body and does nothing. Everything in the
table therefore arrived over `POST`.

### Normalisation

`normalizeTagName` in `src/trending-tags/utils/tag-name.util.ts` does, in order:

```text
camelCase -> kebab-case   (\p{Ll})(\p{Lu})  ->  $1-$2
uppercase
drop everything that is not a letter, a number or "-"   (any script)
collapse runs of "-" and trim leading/trailing "-"
```

So `CamelCase` becomes `CAMEL-CASE`, `dog` plus an emoji becomes `DOG`, `привет` becomes
`ПРИВЕТ`, and `!!!` becomes the empty string — which ingest skips with an error entry rather
than storing. Non-Latin scripts survive: this is deliberate, because the CHINESE, ARABIC and
RUSSIAN collections mint tokens whose names are not Latin, and the tag has to come out equal to
the token name for the join to resolve. See
[Collections and naming](/tokens/collections-and-naming).

### `POST /api/trending-tags` requires an API key

It is guarded by `ApiKeyGuard`
(`superhero-api/src/trending-tags/guards/api-key.guard.ts`). Send the key as either header:

```bash
curl -s -X POST "https://api.superhero.com/api/trending-tags" \
  -H "x-api-key: YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{"provider":"x","items":[{"tag":"SuperHero","score":"95.5"}]}'
```

`Authorization: Bearer YOUR_KEY` is accepted as an alternative. The guard compares the value in
constant time against the server's `TRENDING_TAGS_API_KEY` and throws `401` when the key is
missing, wrong, or when the server's own key is unset or shorter than 16 characters — a
misconfigured deployment fails closed rather than open.

The response is a summary, not the stored rows:

```json
{
  "message": "Trending tags processing completed",
  "results": { "created": 18, "updated": 0, "total_processed": 20, "errors": ["Tag \"!!!\" resulted in empty normalized tag"] }
}
```

Remember that this call replaces the entire table.

## From a tag to a token

There is no single "resolve tag to token" endpoint. Three routes, in the order the web app and
the agent skill use them:

1. **Read the nested `token` off the tag row.** The list endpoint already joins it on
   `token.name = trending_tag.tag`. Free, but only on the list — the single-tag route does not
   join.
2. **Look the name up directly.** `GET /api/tokens/{name}` resolves a token by name, not just by
   address, and 404s cleanly when no token exists. This is what
   `superhero-token-swap.mjs lookup` does first.
3. **Search.** `GET /api/tokens?search={tag}` matches on name, for partial and fuzzy cases.

Posts go the other way for free: every `PostDto` carries `trend_mentions`, an array that already
resolves each `#hashtag` in the body to a `sale_address`, its `collection_info` and a
`performance` summary. See [Posts](/api-reference/posts).

## The trending-score formula

The tag `score` and a token's `trending_score` are different numbers with nothing in common. The
tag score is a provider's opinion, passed through. `TokenDto.trending_score` is computed by the
backend, from Superhero's own data, with a published formula.

It is the default sort for the trending token list:

```bash
curl -s "https://api.superhero.com/api/tokens?order_by=trending_score&order_direction=DESC&limit=10"
```

That is exactly what `superhero-trending.mjs tokens` calls.

### Shape and range

```text
normalized(x, cap) = ln(1 + min(x, cap)) / ln(1 + cap)

trading_score = 0.40*normalized(active_wallets, 25)
              + 0.20*normalized(buy_count, 40)
              + 0.20*normalized(sell_count, 40)
              + 0.20*normalized(volume_ae, 5000)

social_score  = 0.32*normalized(mention_posts, 15)
              + 0.32*normalized(mention_comments, 50)
              + 0.22*normalized(unique_authors, 20)
              + 0.05*normalized(tips_count, 15)
              + 0.03*normalized(tips_amount_ae, 250)
              + 0.06*normalized(reads, 200)

pre_decay     = 0.35*trading_score + 0.65*social_score

freshness     = 1 / (1 + age_hours / 2) ^ 1.15        when pre_decay > 0, else 0

trending_score = round(pre_decay * freshness, 6)
```

Every weight set sums to 1 and every `normalized(...)` term lies in `[0, 1]`, so `pre_decay` lies
in `[0, 1]`; `freshness` is at most 1 (at zero age) and falls monotonically. **`trending_score`
is therefore a decimal in `[0, 1]`, rounded to six places.** A score of 0 means either no
activity in the window or a non-finite computation, which the writer coerces to 0.

**It is comparable across tokens.** The caps, weights and decay constants are module-level
constants shared by every token — there is no per-token or per-universe normalisation, and
nothing in the calculation depends on what other tokens are doing. That is the deliberate
improvement over the previous min-max formula, which divided by a platform-wide range and
produced `NaN` when the range collapsed.

It is *not* comparable across time without care: the same activity scores lower an hour later,
because `age_hours` is measured from the most recent qualifying event at read time.

### Inputs

The window is the **last 24 hours** (`WINDOW_HOURS: 24`).

| Signal | Cap | Weight | Source |
| --- | --- | --- | --- |
| `active_wallets` | 25 | 0.40 of trading | `COUNT(DISTINCT address)` over the token's transactions |
| `buy_count` | 40 | 0.20 | transactions with `tx_type = 'buy'` |
| `sell_count` | 40 | 0.20 | transactions with `tx_type = 'sell'` |
| `volume_ae` | 5000 | 0.20 | `SUM(amount->>'ae')` over `buy`, `sell` and `create_community` |
| `mention_posts` | 15 | 0.32 of social | top-level posts whose body mentions the symbol |
| `mention_comments` | 50 | 0.32 | comments anywhere in a thread rooted on such a post |
| `unique_authors` | 20 | 0.22 | distinct `sender_address` across those posts and comments |
| `tips_count` | 15 | 0.05 | tips on those posts, excluding self-tips |
| `tips_amount_ae` | 250 | 0.03 | `SUM(amount)` of those tips |
| `reads` | 200 | 0.06 | `post_reads_daily` rows for those posts |

Trading is worth 0.35 of the total and social 0.65 — social activity dominates by design.

Attribution is by direct `#SYMBOL` mention. There is no persisted post-to-token foreign key; a
top-level post that mentions the symbol becomes the root of a token thread, and every
non-hidden comment, tip and read anywhere in that thread then counts for the token, whether or
not it repeats the hashtag.

### When it is recomputed

| Trigger | Cadence |
| --- | --- |
| A trade, post, comment or tip involving the token | immediately, via the `update-trending-scores` Bull queue, deduped per symbol with a 5-second delay |
| `ACTIVE_REFRESH_CRON` — tokens with activity in the last 120 minutes | `0 */2 * * *`, every two hours, up to 250 tokens |
| `STALE_BACKFILL_CRON` — tokens whose score is older than 30 minutes | `30 */6 * * *`, every six hours, up to 150 tokens |
| `GET /api/tokens/{address}/score` | on demand, and it persists the result |

Because decay is applied at write time rather than read time, a token with no new activity keeps
a stale score until one of the backfill paths reaches it. `trending_score_update_at` tells you
how stale.

All of the constants above live in `TRENDING_SCORE_CONFIG` in
`superhero-api/src/configs/constants.ts`; the calculation is
`TokensService.calculateTokenTrendingMetrics`. A design note shipped with the backend explains
the reasoning: `superhero-api/docs/bcl-trending-score.md`. Note that that document's "Current
configuration" section quotes an older cron (`*/2 * * * *`) and lookback (15 minutes) than the
code; the constants file is the one that runs.

### Which tokens are eligible

Sorting by `trending_score` applies a gate before the sort: at least **5 holders**, **2** all-time
posts mentioning the symbol and **3** all-time trades
(`TOKEN_LIST_ELIGIBILITY_CONFIG`). `GET /api/tokens/{address}/trending-eligibility` shows one
token's standing against those thresholds. If no token at all clears the gate the list is
re-queried without it, so the trending tab is never empty.

## Topics

A topic is a hashtag that exists because someone posted it, with a post count attached.

| Parameter on `GET /api/topics` | Notes |
| --- | --- |
| `order_by` | `name`, `post_count`, `created_at` |
| `order_direction` | `ASC` or `DESC` |
| `search` | Substring match on the name |
| `limit`, `page` | Standard pagination |

`GET /api/topics/name/{name}` returns one topic with a `posts` array and a `post_count` number.
The web app uses `post_count` when it is a number and otherwise falls back to the length of
`posts`, so treat the count as advisory. `GET /api/topics/{id}` accepts a UUID **or** a name, and
`GET /api/topics/popular/trending` is a ready-made "most used" list with no parameters.

```bash
curl -s "https://api.superhero.com/api/topics/name/superhero"
curl -s "https://api.superhero.com/api/topics?order_by=post_count&order_direction=DESC&limit=20"
```

A topic row is `TopicDto` (`superhero-api/src/social/dto/topic.dto.ts`), backed by the `topics`
table:

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string | UUID |
| `name` | string | The hashtag, unique, at most 100 characters |
| `description` | string or null | At most 500 characters |
| `post_count` | number | Posts carrying this topic |
| `token` | `TokenDto` or null | The token whose symbol matches this topic name, when one exists |
| `created_at` / `updated_at` | string | ISO 8601 |
| `version` | number | Indexer bookkeeping |

The `token` relation is marked `persistence: false` — it is resolved for reads and never written
through, so it is the topic-side equivalent of the trending tag's nested `token`.

## `GET /api/search`

One request across all three entity types, run in parallel server-side:

| Parameter | Notes |
| --- | --- |
| `q` | Search term, max 100 characters. A `q` shorter than 2 characters returns empty arrays |
| `limit` | Max results **per category**, clamped to 1–20, default 5 |

Returns `SearchResultDto`: `tokens` (full `TokenDto` objects), `accounts`
(`address` plus `chain_name`) and `posts` (full `PostDto` objects).

```bash
curl -s "https://api.superhero.com/api/search?q=super&limit=5"
```

For a trend-discovery loop this is often a better first call than three separate requests.

## Open questions

- **Which providers hold a `TRENDING_TAGS_API_KEY` in production?** The backend imposes no
  allow-list on `provider` and pulls nothing itself, so the `source` values in the live table are
  whatever the key-holders send. Only the API operators know who holds a key; the values in the
  Swagger example (`x`, `facebook`, `github`) are illustrative. Reading `GET /api/trending-tags`
  and collecting the distinct `source` values shows who posted most recently, but because ingest
  truncates the table that is one provider at a time, not the full set.
