# Profiles & Accounts

Every æternity address has a profile page on Superhero whether or not anyone has ever set it
up. This page documents what those pages show, where each field comes from, how you edit your
own, and how the leaderboards rank accounts.

## The two profile surfaces

| Route | What it is |
| --- | --- |
| `/users/:address` | The social profile: header, feed, owned and created tokens, transactions |
| `/user/:address` | Legacy path; redirects to `/users/:address` |
| `/trends/accounts` | The trader index — every account with token activity |
| `/trends/accounts/:address` | The Trendminer view of an account, focused on trading |
| `/trends/leaderboard` | Ranked accounts by portfolio performance |

Live: the social profile is at `https://superhero.com/users/` followed by an `ak_` address.

## The header

| Element | Source |
| --- | --- |
| Display name | The linked preferred AENS name, else `public_name`, else the AENS name resolved for the address, else a shortened `ak_…` |
| Verified badge | Rendered when an X link resolves for the account |
| Bio | `links.bio`, falling back to `profile.bio` and then the account's own `bio` |
| Website | `links.site` |
| Avatar | The profile's `avatarurl`, with a deterministic generated fallback |
| Balances and counts | The account aggregate — holdings count and total created tokens |

The account aggregate served by `GET /api/accounts/{address}` carries `address`, `bio`,
`chain_name`, `chain_name_updated_at`, an embedded `profile`, `public_name`, `holdings_count`,
and a `links` object keyed by the `AddressLink` provider ids — `x`, `nostr`, `bio`, `site` and
`prefaens`. The `links` object is authoritative: the client reads it first and treats the flat
fields as fallbacks for older records.

The endpoint also self-heals the chain name. If `chain_name_updated_at` is older than the
staleness window, or has never been set, it re-reads the name from the middleware, returns the
fresh value, and writes it back asynchronously. An hourly sweep in `AccountService` covers the
same ground for accounts nobody is currently viewing, so a lapsed or transferred `.chain` name
disappears from a profile within about an hour.

## The tabs

`/users/:address` has four tabs, selected by a `tab` query parameter (`feed` is the default and
omits the parameter):

| Tab | Value | Contents |
| --- | --- | --- |
| Feed | `feed` | The account's posts and on-chain activity items |
| Owned | `owned` | Tokens the account holds, ordered by balance |
| Created | `created` | Tokens the account created |
| Transactions | `transactions` | The account's trades, with the token expanded |

All four datasets are prefetched in the background when the page loads, so switching tabs is
instant. The feed tab merges posts from `GET /api/posts?account_address=…` with trade and
token-creation activity items.

## On-chain versus API

| Field | Where it lives |
| --- | --- |
| Preferred AENS name, bio, website, X handle, Nostr key | `AddressLink` contract state, as provider links — signed by you, submitted by the backend |
| AENS name ownership and pointers | æternity AENS |
| Chain name shown on a profile | Derived from the middleware and cached in `accounts.chain_name` — not a contract link |
| Fullname, avatar URL, legacy username, `chain_expires_at` | The frozen `profile_cache` table. Its writer, the ProfileRegistry indexer, was removed. |
| Follower and following counts | The social-graph tables, when that feature is enabled |
| Posts and comments | `Tipping` v3 contract, indexed by the API |
| Balances, portfolio history, leaderboard stats | Computed by the API from chain data |

There is no field on a profile that the API can change on its own behalf. Everything a user
controls is behind a wallet signature they produced — though note that the *submission* of that
signature is done by Superhero's provider wallet, the only account permitted to write those
provider namespaces. See [The AddressLink contract](/identity/profile-registry).

## Editing your own profile

The editor is the **Edit SuperheroID** action on your own profile. It is one modal over several
independent operations, not a single save:

| Field | How it is written |
| --- | --- |
| Bio | Claim at `/api/address-links/bio/claim`, sign the returned message, submit at `/bio/submit` |
| Website | The same pair under `/api/address-links/site/`, with the scheme stripped from the stored value |
| Preferred `.chain` name | The same pair under `/api/address-links/prefered-aens-name/`, which uses `link_principal` and verifies AENS ownership on chain |
| X handle | The OAuth flow — see [Verifying Your X Account](/identity/x-verification) |
| Nostr key | The same pair under `/api/address-links/nostr/`, with a signed kind-22242 event as the extra proof |

Each link has a matching unlink: `/unclaim` returns a message and nonce, you sign it, and
`/unclaim/submit` relays the removal. Because the operations are independent, a partial failure
is possible — the bio can save while the website call fails — and the editor reloads its state
afterwards rather than assuming the form is authoritative.

Every claim reads the contract's own `get_nonce(address)`, and the nonce advances on each link
or unlink. If two devices claim at once the second submit fails with a nonce mismatch and has
to restart from claim.

**Fullname, avatar and the legacy username are not editable.** The app's REST inventory lists
`POST /api/profile/{address}/challenge` and `PATCH /api/profile/{address}` as a deprecated
legacy pair, but neither route exists in `superhero-api` at all — the profile controller has
only the two read endpoints, the profile feed, the X-invite endpoints, the two progress
endpoints and the `chain-name` claim flow. Those three fields live in the frozen `profile_cache`
table and no live endpoint writes them.

## Leaderboards

`/trends/leaderboard` ranks accounts by portfolio performance from
`GET /api/accounts/leaderboard`.

| Query parameter | Values |
| --- | --- |
| `window` | `7d`, `30d` or `all` |
| `sortBy` | `pnl`, `roi`, `aum` or `mdd` |
| `sortDir` | `ASC` or `DESC` |
| `points` | Sparkline resolution — 7 for a week, 30 otherwise |
| `page`, `limit` | Pagination; the client asks for 18 per page |

Each row carries `address`, `chain_name`, `aum_usd`, `pnl_usd`, `roi_pct`, `mdd_pct`,
`buy_count`, `sell_count`, `volume_usd`, `created_tokens_count`, `owned_trends_count` and a
`portfolio_value_usd_sparkline` of timestamp-value pairs.

Two details worth knowing before you read a ranking. The default sort direction is descending
for every metric except maximum drawdown (`mdd`), which sorts ascending because a smaller
drawdown is better. And the ranking is portfolio performance only — it says nothing about
posting, tipping or governance participation.

## The account index

`/trends/accounts` reads `GET /api/accounts`, which pages at 1 to 100 rows and accepts a
`search` term matched against the address, `accounts.chain_name` and the cached
`public_name` / `username` / `fullname`. The ranking is trading activity, and `order_by` takes
exactly nine values — anything else is a 400:

| `order_by` | Ranks by |
| --- | --- |
| `total_volume` | Trade volume — **the default** |
| `total_tx_count` | All trades |
| `total_buy_tx_count` | Buys only |
| `total_sell_tx_count` | Sells only |
| `total_created_tokens` | Tokens the account created |
| `total_invitation_count` | Invitations created |
| `total_claimed_invitation_count` | Invitations redeemed |
| `total_revoked_invitation_count` | Invitations revoked |
| `created_at` | When the account row first appeared |

`order_direction` is `ASC` or `DESC`, defaulting to `DESC`. There is one more filter worth
knowing: `has_nostr=true` returns only accounts that have linked a Nostr key, which is what a
chat-contact suggester wants.

Note what is absent — nothing ranks by posting, commenting, tipping or governance. Both the
account index and the leaderboard are trading surfaces.

## How `public_name` is computed

Server-side, by a fixed four-step ladder in `ProfileReadService`, with no per-account
preference involved:

```text
prefered_aens_name   (links.prefaens — the AENS name the user explicitly linked)
chain_name           (accounts.chain_name, derived from the middleware)
username             (the frozen registry-era cache field)
address              (the ak_… itself)
```

The registry's `display_source` preference has no successor — the field is not in the response
and there is nothing to set. See [Names](/identity/names).
