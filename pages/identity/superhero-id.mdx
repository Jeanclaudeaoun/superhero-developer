# SuperheroID

SuperheroID is the name Superhero gives to its identity layer: an æternity address with a set
of independently signed, independently revocable links attached to it. Today those links live
in the `AddressLink` contract, not in `ProfileRegistry.aes` — the registry was superseded and
its indexer removed. This page covers what an identity actually contains now, which parts are
on chain, and how much of the marketing claim the code supports.

## What the product claims

The landing page makes three claims:

> A DID (decentralized identifier) that links your social accounts to your wallet. Your
> identity is verifiable, portable, and censorship-resistant — following the W3C standard
> for decentralized identifiers.

- W3C DID standard compliant
- Links wallet, chain names and X handle
- Self-sovereign — you control your data

The in-app help text is more concrete:

> SuperheroID is a decentralized digital identity smart contract that connects all your social
> accounts to your wallet address. Your SuperheroID Profile will be set up automatically for
> you after linking your X account.

The linking claim holds up. The self-sovereignty claim holds up for the *authorisation* — every
link requires your signature and only you can remove it — but not for the *submission*: the
transaction is sent by a provider wallet Superhero controls, and that wallet is the only
account permitted to write into the `x`, `nostr`, `bio`, `site` and `prefaens` namespaces. The
W3C claim is asserted and not specified anywhere; see
[DIDs and the W3C Standard](/identity/did-standard).

## What it links

| Link | Provider id | On-chain call | Proof required |
| --- | --- | --- | --- |
| X handle | `x` | `link` | An OAuth session the backend observes, sealed into a 5-minute HMAC token |
| Nostr key | `nostr` | `link` | A kind-22242 event signed by the npub, under 5 minutes old |
| Preferred `.chain` name | `prefaens` | `link_principal` | AENS ownership, checked on chain with `AENSv2.lookup` |
| Bio | `bio` | `link` | Ownership of the address only |
| Website | `site` | `link` | Ownership of the address only |

Every one of those also needs your æternity signature over the claim message, so the table's
"proof" column is what the provider adds *on top of* proving you hold the key. Each link is
removed by its own `unlink`, which needs nothing but your signature.

Two things the whitepaper describes are **not in this list because they no longer exist**:

- **Custom names.** There is no custom-name namespace in `AddressLink`, no `set_custom_name`,
  and therefore no auto-rename and no `CustomNameAutoRenamed` event. The `profile.username`
  field survives in the API as a frozen cache column with no writer.
- **Display source.** `set_display_source` is gone and `display_source` is not in the profile
  response. A public name is chosen by a fixed server-side ladder, not by your preference.

See [The AddressLink contract](/identity/profile-registry) for the full before-and-after.

## What is on chain and what is not

| Data | Authority |
| --- | --- |
| Every provider link, its value, and the per-address nonce | `AddressLink` contract state |
| The reverse index — which address owns a given provider value | `AddressLink` contract state |
| Which account may write a provider namespace | `AddressLink` `providers` map |
| AENS name registration, pointers, expiry | æternity AENS — the `prefaens` link references it, it does not own it |
| Posts, comments, tip totals | `Tipping` v3 plus the API index |
| Avatar, fullname, legacy username, follow counts, leaderboard stats | Superhero API |
| Chain name shown on a profile | Derived hourly from the middleware, not from any contract link |

`GET /api/profile/{address}` serves the merged aggregate: `address`, a `profile` object
(`fullname`, `bio`, `site`, `avatarurl`, `username`, `prefered_aens_name`, `x_username`,
`chain_name`, `chain_expires_at`, plus follow counts when the social-graph feature is on) and a
resolved `public_name`. Its `includeOnChain` query flag is documented as deprecated: profiles
are served entirely from indexed backend data, so there is nothing left to opt into.

`public_name` is resolved by this ladder, in `ProfileReadService`:

```text
prefered_aens_name   (links.prefaens — the AENS name you explicitly linked)
chain_name           (accounts.chain_name, from the middleware, refreshed hourly)
username             (the frozen registry-era cache field)
address              (the ak_… itself)
```

`GET /api/accounts/{address}` returns the raw side of the same thing, including the `links`
object keyed by provider id. That is the authoritative view — the client reads it first and
treats the flat profile fields as fallbacks for older records.

## How a third party verifies a claim

Nothing here requires trusting Superhero's *API*, but some of it requires trusting Superhero's
*provider wallet*. The difference matters:

1. **Preferred `.chain` name.** Strongest. The link was written by `link_principal`, which
   calls `AENSv2.lookup` inside the contract and aborts with `PRINCIPAL_MISMATCH` if the signer
   does not own the name. You can independently resolve the name through AENS on any node and
   compare its `account_pubkey` pointer. Both checks are protocol state.
2. **Nostr key.** Strong off chain, weak on chain. The backend verified a Schnorr signature
   from the npub over the exact claim message before submitting, but only the æternity
   signature is recorded. A third party reading the chain sees consent to an npub string, not
   proof of the Nostr key.
3. **X handle.** Weakest. The chain records that the address consented to a handle string and
   that the provider owner submitted it. The OAuth evidence lives only inside the backend and
   is discarded. See [Verifying Your X Account](/identity/x-verification).
4. **Bio and website.** Nothing to verify beyond ownership of the address.
5. **Posts.** Independent of all of the above — a post's `sender` is whichever address signed
   the transaction, recorded by the `Tipping` contract.

That ladder is the whole trust model. A verified badge in the UI means "an X link resolves for
this account", not "this person is who they say they are".

## Where you manage it

In the app, SuperheroID lives behind the **Edit SuperheroID** action on your own profile at
`https://superhero.com/users/` plus your address. The modal covers the `.chain` name selection
and preferred-name link, the bio, the website link, and the X connection. Each change is a
separate claim-sign-submit round trip, not one bulk save — a failure part-way through can leave
the bio linked and the website not, which is why the editor reloads its state afterwards rather
than trusting the form.

The fields that have no writer any more — fullname, avatar, the legacy username — are not
editable through any live endpoint.
