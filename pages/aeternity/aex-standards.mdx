# AEX Standards

AEX ("æternity expansion") proposals are æternity's application-layer standards, the equivalent
of Ethereum's ERCs. Superhero depends on one of them heavily — **AEX-9**, the fungible token
standard — and touches a few others through its wallet stack.

## AEX-9 — fungible tokens

Every Superhero community token and the ProtocolDAO token is an AEX-9 contract. That is why a
token you mint on Superhero shows up in any æternity wallet and on
[æScan](https://aescan.io/) without Superhero having to integrate with them.

AEX-9 was written in 2019 and is explicitly inspired by ERC-20, but it is deliberately smaller:
the base interface is the read functions plus `transfer`, and everything else — allowances,
minting, burning, swapping — is an optional extension. A contract advertises which extensions it
implements at runtime through `aex9_extensions()`.

### The interface, from a real deployed contract

Read directly off `superhero-agent-skill/contracts/FungibleTokenFull.aci.json`, the ACI the
agent skill uses to talk to Superhero's tokens. "Stateful" means it needs a signed transaction;
everything else can be dry-run for free.

**Reads**

| Entrypoint | Returns | Notes |
| --- | --- | --- |
| `aex9_extensions()` | `list(string)` | Which optional extensions this contract implements |
| `meta_info()` | record | `name`, `symbol`, `decimals` |
| `total_supply()` | `int` | In token-decimals, not whole tokens |
| `owner()` | `address` | The minting authority |
| `balance(account)` | `option(int)` | **An option, not an int** — see below |
| `balances()` | map | Every holder at once |
| `allowance(accounts)` | `option(int)` | Keyed on a from/for pair |
| `allowance_for_caller(from)` | `option(int)` | Convenience for the common case |
| `allowances()` | map | Every allowance at once |
| `swapped()` | map of address to int | Migration bookkeeping |

**Writes (all stateful)**

| Entrypoint | Extension | Purpose |
| --- | --- | --- |
| `transfer(to, value)` | base | Move your own tokens |
| `create_allowance(for, value)` | allowance | Authorise a spender |
| `change_allowance(for, delta)` | allowance | Adjust by a delta |
| `reset_allowance(for)` | allowance | Revoke |
| `transfer_allowance(from, to, value)` | allowance | Spend someone else's authorised balance |
| `mint(account, value)` | mintable | Owner only |
| `burn(value)` | burnable | Destroy your own |
| `swap()` | swappable | Migrate a legacy balance |
| `check_swap(account)` | swappable | Inspect a migration |

`init(name, decimals, symbol, initial_owner_balance)` is the deploy-time constructor;
`initial_owner_balance` is an `option(int)`.

### How AEX-9 differs from ERC-20 in practice

Four things will bite you if you port ERC-20 assumptions directly:

1. **`balance` returns an option.** An address that has never held the token returns `None`, not
   `Some(0)`. Handle the empty case explicitly, or a new user's balance lookup breaks instead of
   showing zero.
2. **Allowances are three calls, not one.** ERC-20's `approve` is split into
   `create_allowance` (for an allowance that does not exist yet), `change_allowance` (relative)
   and `reset_allowance`. There is no single idempotent setter, so you must know whether an
   allowance already exists before you write one.
3. **`transfer_allowance` is `transferFrom`.** Same withdraw pattern, different name.
4. **Extensions are declared, not assumed.** Call `aex9_extensions()` before assuming `mint` or
   `burn` exists. A minimal AEX-9 token has neither — the reference `fungible-token.aes` returns an
   empty list. Superhero's own stack spans the range: a community token returns four extensions,
   while the DEX's [WAE contract](/defi/wrapped-ae) and every
   [liquidity-pool token](/defi/pools) return `["allowances"]` and nothing else, because their
   supply changes only through deposit, withdraw, mint and burn paths that are not AEX-9
   entrypoints.

Also, as everywhere on æternity: amounts are integers scaled by the token's own `decimals` from
`meta_info()`, which is not necessarily 18. See [AE & Gas](/aeternity/ae-and-gas).

### Which extensions a Superhero community token needs

Every community token is created by the sale contract as a `FungibleTokenFull`
(`Chain.create(name, decimals, symbol, None) : FungibleTokenFull` in
`bcl-contracts/contracts/AffiliationBondingCurveTokenSale.aes`), and the ProtocolDAO token the same
way in `CommunityFactory.init`. `FungibleTokenFull` is the reference implementation's "full"
variant, pulled in from `aeternity/aeternity-fungible-token` at tag **v2.2.0**
(`bcl-contracts/package.json`). At that tag, `contracts/fungible-token-full.aes` declares:

```sophia
entrypoint aex9_extensions() : list(string) = ["allowances", "mintable", "burnable", "swappable"]
```

So `aex9_extensions()` on any Superhero community token returns those four strings, in that order.
Superhero's own contracts exercise the first three:

| Extension | Where the protocol depends on it |
| --- | --- |
| `mintable` | `buy` calls `token_contract.mint(Call.caller, count)` |
| `burnable` | `sell` calls `token_contract.burn(count)` |
| `allowances` | `sell` calls `transfer_allowance`; `DAOVote.vote` locks tokens the same way |
| `swappable` | Nothing in the Superhero stack calls `swap` or `check_swap` — it comes with the variant |

A Superhero community token therefore cannot be a minimal AEX-9: remove any of the first three and
buying, selling or voting stops working. `swappable` is inherited baggage from the reference
contract's token-migration support, and is worth knowing about only so that a fourth string in the
list does not surprise you.

`decimals` is fixed at **18** for every community token: `CommunityFactory.decimals()` returns 18
and the sale contract's `init` enforces `decimals == bonding_curve.supported_decimals()`, which is
also 18.

### Reading AEX-9 balances without a contract call

The middleware indexes AEX-9 holdings, so a wallet view does not need one contract call per
token. The web app fetches them in a single paged request
(`src/hooks/useAccountBalances.ts`):

```text
GET  <MIDDLEWARE_URL>/v2/aex9/account-balances/ak_...?limit=100
```

Note the `v2` — the AEX-9 balance route the app uses is on middleware v2 while its transaction
lookups use `v3`. See [Networks & Endpoints](/aeternity/networks).

## The other AEX standards

Statuses are as recorded in the index table of the
[AEXs repository](https://github.com/aeternity/AEXs) README at its current `master` head, which
was last changed in November 2022. AEX-1 defines the terms: **Review** means past initial
iteration and under wide review, **Active** means in constant flux with no unaddressed objections,
**Final** means it sat in Last Call for two weeks with every technical change addressed.

| Standard | Subject | Status | Superhero's relationship to it |
| --- | --- | --- | --- |
| AEX-2 | Wallet-to-æpp communication | Withdrawn, but still the js-sdk's reference implementation | Used. `useWalletConnect.ts` runs `walletDetector` over a `BrowserWindowMessageConnection` and calls `aeSdk.connectToWallet` — that is the AEX-2 RPC flow |
| AEX-3 | Encrypted secret storage (keystore JSON) | Active | Not used directly in these repositories; relevant if you import a keystore file |
| AEX-8 | Message signing | Draft | Relevant to any off-chain signature, including the tipping contract's signed messages |
| AEX-9 | Fungible tokens | Review | Used everywhere |
| AEX-10 | BIP32 derivation path for deterministic wallets | Final | Applies to any mnemonic-based æternity wallet used with Superhero — see [Accounts & Keys](/aeternity/accounts-and-keys) |
| AEX-130 | æpp meta-information format | Draft | Not used |
| AEX-141 | Non-fungible tokens | Review | Not used. Superhero has no NFT feature |

**AEX-9 is still "Review", and nothing supersedes it.** The status has not moved since the
standard was written in 2019 — `AEXS/aex-9.md` carries `Status: Review` in its own header, the
README index agrees, and no AEX in the repository carries the `Superseded` status at all. Read
"Review" here as "stable in practice but never formally finalised", not as "in flux": every
æternity wallet, explorer and the middleware's AEX-9 indexing are all built against it as written.
