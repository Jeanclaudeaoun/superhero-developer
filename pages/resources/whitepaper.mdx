# Whitepaper

The Superhero technical whitepaper, **version 0.7, February 2026**, is published in-app at
[superhero.com/whitepaper](https://superhero.com/whitepaper). It is the best available prose
description of the protocol, and most of these docs are built from it. Use this page to find the
right section fast, to jump from a section to the page that expands it, and — the section that
matters most below — to see where it no longer matches the deployed contracts.

**Order of authority:** the Sophia sources are the specification, the whitepaper is a description of
them, and this site is a description of both. Where they disagree, believe the `.aes`. Every
divergence listed below was found by reading the contracts, and each one names the file so you can
check it yourself.

The whitepaper renders as Markdown with GitHub-flavoured tables and KaTeX math in the app itself.
There is no PDF — see the open questions.

## Where the whitepaper diverges from deployed code

All ten BCL Sophia sources are readable, so these are checkable claims rather than suspicions. None
of them is large enough to change what the protocol *is*; several will change a number you compute.

| # | Whitepaper says | The contracts do | File |
| --- | --- | --- | --- |
| 1 | Six vote subjects | **Seven.** `ChangeMetaInfo(map(string, string))` — a vote to change a community's metadata — is implemented but never mentioned | `DAOVote.aes` |
| 2 | ProtocolDAO issuance is "1,000 × the AE value of each buy" | 1,000 × the **all-in** AE debited, affiliation fee included — so 1,005× the curve price. The app displays 950× | `CommunityFactory.aes`, `superhero/src/utils/constants.ts` |
| 3 | The buy curve is `0.001 * e^(0.00000001 * x) - 0.0009999` | The contract evaluates a **bounded Maclaurin series**, not that closed form: `curve_type()` returns `"TAYLOR_EXPONENTIAL_V1"` and the expansion stops at 100 terms | `BondingCurveExponential.aes` |
| 4 | Not mentioned | `get_sell_return_precision()` returns `sell_return_percentage` (9950) instead of `sell_return_precision` (10000). **On-chain sell math is correct** — `calculate_sell_return` uses the constants directly — but an off-chain caller that derives the ratio from the two getters computes 1.0 and overstates sell returns by 0.5% | `BondingCurveExponential.aes` |
| 5 | "If no referrer: burned" | Two further amounts burn the same way and neither is mentioned: rewards go unclaimable after two 30-day payout periods, and an inviter cannot withdraw at all until four distinct invitees have each bought ≥ 10 AE | `AffiliationTreasury.aes` |
| 6 | "The protocol's contract suite is designed for independent audit and formal verification" | Every source file carries the header **"THIS IS NOT SECURITY AUDITED — DO NEVER USE THIS WITHOUT SECURITY AUDIT FIRST"**, followed by a full liability disclaimer | all ten `.aes` files |
| 7 | Describes the 555 AE cost of opening a DAO vote | The same 555 AE is also required to **create a collection**, and unlike the vote donation it is sent to `ak_11111111111111111111111111111111273Yts` — burned, not paid to anyone. The whitepaper does not mention a collection creation cost | `CommunityFactory.aes` |
| 8 | Not mentioned | A vote's `description` is capped at **300 characters** by `init`; longer proposals abort | `DAOVote.aes` |
| 9 | 99.0% / 0.5% / 0.5% | 99.005% / 0.4975% / 0.4975% of what the buyer sends. The whitepaper's figures are that split rounded | `AffiliationBondingCurveTokenSale.aes` |
| 10 | Not mentioned | There is a **minimum tradable amount**: `minimum_count = 10^12` aettos, or 10^-6 of a token. Anything smaller aborts with `MINIMUM_TOKENS_REQUIRED` | `BondingCurveExponential.aes` |
| 11 | A backend relayer submits signed posts through `post_without_tip_sig` | `superhero-api` implements no such endpoint; the backend never broadcasts a post. The contract entrypoint is real but unused | `superhero-api/src/` |
| 12 | Identity is `ProfileRegistry.aes` | The backend's identity indexer targets a different contract — `AddressLink`, a provider-keyed linking contract with per-provider nonces and signature-authorised `link` / `unlink`, plus DID and principal variants | `superhero-api/src/plugins/address-links/` |

Items 2, 3 and 4 are the ones that will bite an integration. Items 6 and 11 are the ones to raise
before you rely on a claim in a risk assessment.

## How to read it

If you are **new to the product**, read Abstract, Introduction and Design Principles, then stop and
come back to this site — the middle sections assume you know what a bonding curve is.

If you are **building an integration**, the useful sections are Superhero Onchain ID, Posting &
Tipping, Community Factory, and System Architecture. They describe data models and deployment
structure; they do not give you entrypoint signatures, which are in the ACIs shipped with the
agent skill and documented under [Smart Contracts](/contracts).

If you are **trying to reconcile a number**, go straight to Exponential Bonding Curve and Token
Economics Summary, then to [Where the Money Goes](/concepts/value-flow), which works the same
arithmetic through a concrete trade and flags the places where the app's behaviour and the
whitepaper's rounding differ.

If you are **assessing risk**, read Security Considerations alongside the honest caveats in
[Risks](/tokens/risks) and the failure modes in [Attention Markets](/concepts/attention-markets).
Note the whitepaper's own wording: the contract suite is "designed for independent audit and formal
verification" — designed for, not audited. The contracts are blunter than that. Every one of the ten
`.aes` files opens with "THIS IS NOT SECURITY AUDITED / DO NEVER USE THIS WITHOUT SECURITY AUDIT
FIRST" and a disclaimer of all liability by BCTSL, the copyright holder. Take the contract headers
as the current audit status until a published report says otherwise.

## Open questions

- **Is there a downloadable PDF?** The whitepaper is a Markdown string rendered client-side in
  `src/views/Whitepaper.tsx`. No PDF asset exists in the repository's `public/` directory and no
  download link appears in the app. Only Superhero can publish one.
- **Is there a version history?** The document is labelled "Version 0.7 — February 2026" with no
  changelog, and versions 0.1 through 0.6 are not published anywhere in these repositories. A reader
  who needs to know what changed between versions has nothing to compare against. Superhero would
  have to publish the earlier revisions or a changelog.
- **Are the divergences above intended, or is the whitepaper simply behind the code?** Each row is a
  factual difference; none of them says which side is the mistake. Only the authors can say whether,
  for example, the ProtocolDAO multiplier is meant to apply to the curve price or to the all-in
  price, and whether the app's 950× display is the intended figure.
- **Has any contract been audited since publication?** The contract headers say no, and no report
  appears in any repository. A published audit — with a firm, a date and a commit hash — would close
  this; nothing short of that should.
