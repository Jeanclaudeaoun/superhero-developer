# Support

Most Superhero problems are one of three things: a transaction that did not do what you expected, a
client that is showing stale data, or a wallet that will not connect. Diagnose which one you have
first — it decides where the report goes — then file it with enough detail that someone can
reproduce it without asking you questions.

## Triage first

Work down this list before filing anything. Each step rules out a whole class of problem.

| Check | How | What it tells you |
| --- | --- | --- |
| Did the transaction land? | Look the hash up on [aescan.io](https://aescan.io) (testnet: [testnet.aescan.io](https://testnet.aescan.io)) | If the chain has it and succeeded, the problem is display, not execution |
| Is the backend up? | The status panel in the app footer | The backend indicator goes red when the API has not answered for 60 seconds. A red indicator explains missing feeds, charts and token data |
| Is your device online? | Same panel, blockchain indicator | Driven by the browser's own online state |
| Is it the indexer lagging? | Compare the token page against the contract | Chain state is authoritative; the API can be behind it by a short interval |
| Is it your wallet? | Try a different surface — extension, the app's built-in wallet, or `wallet.superhero.com` | Narrows a signing failure to one wallet |

If the chain shows your transaction as successful and the app disagrees, it is a client or indexer
bug and worth reporting. If the chain shows it reverted, the error is on-chain — a slippage floor
you crossed, a missing allowance, an insufficient balance — and
[Troubleshooting](/wallets/troubleshooting) is the better starting point.

## Where to report

| What | Where |
| --- | --- |
| Bug or feedback about the web app, mobile apps or PWA | [github.com/superhero-com/superhero/issues](https://github.com/superhero-com/superhero/issues) |
| Bug in the API, the indexer or a trending score | [github.com/superhero-com/superhero-api](https://github.com/superhero-com/superhero-api) |
| Bug in the AI agent skill — scripts, guides, ACIs | [github.com/superhero-com/superhero-agent-skill](https://github.com/superhero-com/superhero-agent-skill) |
| Privacy, data-protection or legal questions | `superherowallet@protonmail.com` |
| Errors in this documentation | See [How to Contribute](/contributing/how-to-contribute) |

Superhero publishes no staffed support desk, and none of these trackers is one. They are simply
where the app itself sends reports: the "Send Feedback" button in the footer and the in-app
feedback control both open
`https://github.com/superhero-com/superhero/issues` directly. No response time is promised
anywhere. The backend is open source too
(`superhero-com/superhero-api`), so a wrong figure in an API response — a trending score, a TVL
column, a PnL number — has a public tracker of its own; its `CONTRIBUTING.md` says to "open an issue
or submit a pull request" and names no other contact.

**There is exactly one official social account identifiable from first-party sources, and it is not
a support channel.** The app's own copy for the X posting reward tells you to "tag
`@superhero_chain`" (`superhero/src/locales/en.json`, `profile.x.*`), and the backend treats
`superhero.com` and `superhero_chain` as the qualifying mentions
(`superhero-api/src/profile/profile.constants.ts`). That account is
[x.com/superhero_chain](https://x.com/superhero_chain). Nothing in any repository presents it as a
place to get help, and no Discord, Telegram, forum or chat channel appears anywhere — so treat any
invite claiming to be Superhero support as unverified and use the trackers and the email address
above.

The `superherowallet@protonmail.com` address is given in both the
[terms of use](https://superhero.com/terms) ("For any additional questions, please contact the
Superhero.com team at …") and the [privacy policy](https://superhero.com/privacy), which names it as
the contact for data-subject requests and for questions about the policy. Note that anything you
send there is off-chain data you volunteered, and the privacy policy processes it on a consent basis
and retains it "until the questions have been answered … or, in any other case, until withdrawal of
consent."

## What to include

The FAQ's own answer sets the minimum: "Include the token name, your address, the tx hash, and what
happened." Expand it into this, and your report will be actionable on the first read.

**Always:**

- **What you expected, and what happened instead.** One sentence each. This is the single most
  useful line in any report.
- **The transaction hash**, if a transaction was involved — even a failed one. Without it nobody can
  see what the chain did.
- **Your account address** (`ak_…`). It is public on-chain already; including it costs you nothing
  and saves a round trip.
- **The network.** Mainnet or testnet. They behave differently and have different contract addresses.
- **The exact URL** you were on, including the token symbol or post ID in the path.
- **Surface and version.** Web browser and version, or iOS/Android app, or PWA, or the agent skill.

**For a trading problem, add:**

- The **token name and its sale address** (`ct_…`).
- The **amount** you entered and the **quote** the trade card showed.
- Your **slippage setting** — the default is 1% in the token trade card, 5% on the DEX, and 3% in the
  agent CLI, and a reverted sell is very often a slippage floor doing its job.
- Whether the **allowance step** succeeded, if you were selling. A sell is two transactions; report
  both hashes.

**For a posting problem, add:**

- The **post ID** (the `…_v3` form) or the parent post ID if it was a comment.
- Whether the post appeared on-chain. Check the transaction before assuming it was lost — an indexer
  delay looks identical to a failed post in the feed.

**For an agent problem, add:**

- The **script and subcommand** you ran, and the JSON it printed. Every script emits structured JSON
  on success and a prefixed error on failure.
- The **runtime** driving the skill.
- **Never** include `AE_PRIVATE_KEY`, a mnemonic, or an unclaimed invite link. Invite links carry a
  one-time secret; pasting one into a public issue hands it to whoever reads it first.

## Do not post these anywhere

- Your **private key** or **secret key**, in any form, to anyone, for any reason. No Superhero
  process ever needs it. Anyone asking is attacking you.
- Your **mnemonic** or seed phrase.
- **Unclaimed invite links.**
- Screenshots that show any of the above, including a wallet's reveal screen.

Support can always be given from a public address and a transaction hash. If a "support agent"
insists otherwise, that is the tell.

## Security disclosure

If you have found a vulnerability in a contract, the app or the skill, disclose it privately first —
do not open a public GitHub issue describing an exploitable bug in a live contract that holds user
funds. No repository publishes a `SECURITY.md` or a dedicated security address: not the web app, the
backend, the agent skill, the BCL contracts, the governance contracts or the tipping contract. The
only address any of these sources gives at all is `superherowallet@protonmail.com`, which the terms
and the privacy policy name for legal and data-protection questions.

Two facts should shape how you weigh a finding. The contracts carry no audit: every BCL `.aes` file
opens with "THIS IS NOT SECURITY AUDITED — DO NEVER USE THIS WITHOUT SECURITY AUDIT FIRST" and a
liability disclaimer by BCTSL. And at least one real defect is already in the deployed code —
`get_sell_return_precision()` in `BondingCurveExponential.aes` returns the wrong constant, which is
harmless on chain but wrong for any off-chain caller. See
[Where the Money Goes](/concepts/value-flow) and
[Security Model](/contracts/security) for what the protocol does and does not defend against.

## Open questions

These three can only be closed by Superhero. Nothing in any repository settles them, and no amount
of further code reading will.

- **What are the "official channels listed in the app"?** The FAQ's support answer points at them
  without naming them. Six repositories were searched — the web app and its locale files, the
  backend, the agent skill, the BCL contracts, the governance contracts and the tipping contract —
  and the only official account any of them identifies is `@superhero_chain` on X, named in the
  posting-reward copy rather than as a support route. Superhero must publish the list, or a
  maintainer must confirm it; **do not add a Discord or Telegram link to this page on any weaker
  evidence.** See [Official Links](/resources/links).
- **Is there a security disclosure policy or bug bounty?** No `SECURITY.md`, no security address and
  no bounty programme exists in any of the six repositories. Whether
  `superherowallet@protonmail.com` is monitored for security reports — and by whom — is not
  established anywhere. Closing this means Superhero publishing a `SECURITY.md` or a disclosure
  address; until then, assume a report to that address may sit with a legal or privacy inbox rather
  than an engineer.
- **Is there a response-time expectation?** None is published for any channel. The GitHub trackers
  are public, so their issue history is the only available signal, and it is a signal about past
  behaviour rather than a commitment.
